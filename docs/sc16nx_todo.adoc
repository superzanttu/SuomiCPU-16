= SC16NX: Kiuas16 and the xv6-capable computer
:toc: left
:toclevels: 2
:experimental:

This is the sole development roadmap for SuomiCPU-16. It replaces the former
architecture, C90, and Tank-16 checklists. Specifications, usage instructions,
licenses, and historical reference material remain separate documents; new
development tasks belong here.

The processor is named *Kiuas16* and the graphics device *AinoGPU*. The selected
successor is an RV64-compatible computer capable of running the actual
https://github.com/mit-pdos/xv6-riscv[MIT xv6-riscv operating system], built with
this project's Rust toolchain. It is not real Linux and not merely a Unix-like
shell implemented by the emulator.

IMPORTANT: This document plans future implementation. Creating the roadmap did
not implement RV64, port xv6, rebuild firmware, or repair the applications.
All implementation tasks start unchecked.

== Scope and completion rules

=== Confirmed direction

* SuomiCPU-16 remains the project name. Kiuas16's name does not impose a
  16-bit instruction, register, pointer, or address limit.
* Select RV64 RISC-V compatibility rather than porting xv6 to the custom
  SC-16 ISA. Preserve upstream xv6 behavior and keep changes small, explicit,
  versioned, and independently testable.
* The project's Rust compiler and assembler must build xv6. Production guest
  linking, syscall-stub generation, filesystem construction, and image
  packaging must also use Rust-native tools. No external C compiler,
  assembler, linker, Python, or Perl fallback may satisfy a production build.
  Ordinary Rust host-toolchain prerequisites are allowed.
* QEMU and GCC/binutils may serve as optional independent verification tools,
  never as production guest-build dependencies or substitutes for Rust-built
  release artifacts.
* PC-like BIOS means POST, discovery, setup, persistent configuration, boot
  selection, disk reads, loading, recovery, and a defined OS handoff. It does
  not mean x86 BIOS interrupts or UEFI compatibility.
* Use separate sector-backed boot-volume and root-filesystem images. The
  boot volume contains the kernel ELF; an upstream xv6 root image alone does
  not contain a firmware-loadable kernel.
* Keep an upstream-compatible xv6 configuration and filesystem format.
  Maintain the practical computer's device drivers and versioned larger-file,
  longer-filename filesystem extension as an auditable extension set.
* AinoGPU includes generic hardware-accelerated 3D as well as text, 2D, and
  framebuffer functionality. Software-only guest 3D is not the final target.
* Restore all 17 non-OS programs as xv6 userspace applications. Standalone
  source/image launches remain development and bring-up facilities, not the
  production application model. Old executable compatibility is not required.
* The existing example called SaunaOS in the project request is
  *SisuOS/SaunaShell*. Keep its sources and historical build instructions;
  do not extend it, port it to RV64, or maintain a legacy runner for it.
  It is the explicit exception to the runnable-application requirement.
* Give every emulated hardware device a Finnish sauna-related name. Names
  are presentation identities, not permission to change protocol IDs.

Initial xv6 bring-up uses one hart and 128 MiB of RAM. Multicore is a later
milestone. Real Linux, full POSIX certification, x86 compatibility,
hypervisor/vector extensions, and a complete USB/PCI ecosystem are outside
the required baseline. Browser support is separate from native desktop
acceptance.

=== How to use this checklist

P0:: Required for genuine Rust-built xv6 execution and firmware boot.
P1:: Required for the complete interactive computer and all active programs.
P2:: Broader C90 certification, multicore, and secondary-platform work.

Each nested task has a stable +nx-*+ anchor, affected components, explicit
dependencies, and acceptance criteria. Dependencies refer to completed
behavior, not merely a merged patch or a position in this document.
Independent work may proceed in parallel; section order is not an implicit
dependency. Each parent milestone additionally depends on all its children.

Keep a parent unchecked until every child and its acceptance tests pass.
When closing a task, record the tested revision, target/configuration, exact
command, expected result, and reproducible evidence here. Keep commands,
fixtures, and machine-readable results with their owning tests; do not create
another task list. A parser pass, successful assembly, screenshot, shell
prompt, or old checked box is not sufficient execution evidence.

Required instructions, language features, devices, and input formats that are
not implemented must fail explicitly. Never silently truncate addresses,
invent successful device responses, substitute a host OS service, or hide a
failure behind an external compiler.

=== P0 execution priorities

Prioritize working, reproducible guest milestones rather than the number of
checked tasks. The immediate critical path is the Rust-native compiler,
assembler/linker, and executable guest pipeline. Existing fixed-encoding ROM
fixtures establish useful hardware behavior, but cannot replace compiled
firmware or kernel consumers.

The order below schedules implementation slices within the existing tasks;
it does not introduce another checklist, change P0/P1/P2 classifications, or
relax any task's final acceptance criteria. Phase numbers are not a required
implementation sequence.

. *First: identify and test the smallest missing compiled-guest capability.*
  Inventory the path from a small C source and assembly startup through
  RV64 output, assembly, linking, ROM packaging, and +kiuas16-run+ execution.
  Map each missing capability to <<nx-compiler-boundaries>>,
  <<nx-rv64-codegen>>, <<nx-rv64-assembler>>, <<nx-elf-linker>>, or
  <<nx-rust-build-driver>>. Define a failing execution fixture before
  implementing the next gap; do not begin with the entire xv6 language
  corpus or a broad compiler rewrite.
. *Bring up one compiled ROM guest.*
  Implement only the coherent frontend, typed lowering, ABI, instruction,
  relocation, and startup subset needed by that fixture, extending existing
  shared stages rather than creating a second compiler. Start with integer
  expressions, calls, stack setup, address construction, and volatile MMIO
  access as required by the source. Rust tools must compile, assemble, link,
  and package it for protected-ROM startup; verify exact guest UART output
  and observable call results within an explicit step budget. Unsupported
  constructs and invalid operands must diagnose. Direct ELF loading may
  help isolate failures, but is not ROM-boot acceptance.
. *Extend that guest through storage.*
  Replace the fixed-encoding storage scenario with compiled guest code that
  owns modern Virtio negotiation, queue construction, DMA buffers, completion,
  and reset. Read a known sector from disposable explicitly attached media
  and assert its bytes through UART; extend to write/flush and read-only
  failure with image-content assertions. Keep stdout, traps, backend errors,
  and budget exhaustion observable; do not initialize queues or substitute
  disk operations in the host.
. *Use the working pipeline to complete Phase 0 evidence.*
  Add independently expected LP64D layout/call/ELF execution fixtures for
  <<nx-abi-contract>> and compile real firmware and pinned-kernel consumers
  of the shared definitions for <<nx-device-contract>>. Extend the pipeline
  only as their requirements demand. The small ROM guest is an intermediate
  milestone, not completion of either contract, full Sytyke, or xv6 boot.
. *Grow the same path toward firmware and xv6.*
  Expand <<nx-c-xv6>>, <<nx-rv64-codegen>>, <<nx-rv64-assembler>>,
  <<nx-elf-linker>>, and <<nx-rust-build-driver>> against the pinned source
  inventory. Implement <<nx-boot-images>> and the firmware-owned load/handoff
  path as those consumers become buildable. Complete the remaining CPU and
  device behavior exercised by these guests without concealing unimplemented
  architectural requirements behind a successful boot.

*Dependency interpretation:* Full ABI acceptance needs a compiler/linker,
while compiler tasks depend on the ABI contract. Use the specified ABI and
shared definitions as inputs to incremental implementation; then produce the
independent execution evidence required to close the contract. Apply the same
distinction to device specifications and their compiled consumers. This
permits prerequisite slices across open tasks, not acceptance by assumption.
Do not wait for Phase 0 parent closure before building its missing toolchain
prerequisites.

*Execution and validation discipline:*

* Define each batch's source fixture, expected output/object bytes, failure
  cases, and completion criterion before coding. Finish with guest execution,
  not only parsing, assembly text, or successful object emission.
* Parallelize only independent work with agreed interfaces and separate file
  ownership: CPU conformance, toolchain development, and firmware/device
  integration. Shared ABI, object/relocation, and device-definition changes
  must be coordinated before dependent work proceeds.
* Run focused tests during iteration; run the full serial suite and build/
  format checks at coherent integration checkpoints. Keep changes in small,
  verified commits rather than accumulating disconnected features.
* Record remaining blockers and reproducible evidence under the owning tasks.
  Recount completed children only after acceptance-backed closures; never
  optimize the count by weakening a parent or child gate.

=== Why RV64

A custom-ISA xv6 port would replace architecture-dependent assembly, traps,
page tables, atomics, drivers, ABI assumptions, and substantial toolchain
support. RV64 compatibility retains more upstream behavior and enables
independent reference execution. It is the selected approach, but does not
remove the Rust compiler/assembler/linker work from the critical path.

=== Pinned upstream requirements

The audited xv6-riscv revision is
+e93dabeb98431235c6e1a101cb96c73c923fdbc4+. Pin and record the actual imported
source, license, and local delta before implementation; do not silently
switch to a moving upstream branch. The planned processor, reset, physical
map, translation, trap, and timebase contracts are defined in
link:kiuas16_machine_contract.adoc[Kiuas16 RV64 Machine Contract]; that
specification does not claim implementation.

The build uses +rv64gc+, GNU C99, and +medany+. Required behavior includes
M/S/U privilege, PMP, Sv39, atomics, CSR operations, memory/instruction
fences, Sstc supervisor timer comparison through +stimecmp+, and page-table
A/D updates enabled by +menvcfg.ADUE+. Designing only for an older xv6 timer
implementation is insufficient.

[cols="2,2,3",options="header"]
|===
| Resource | Compatibility value | Requirement
| RAM | +0x80000000+, initially 128 MiB | Sparse physical mapping; no old 30-bit wrapping.
| Höyry UART | +0x10000000+, IRQ 10 | 16550 register/interrupt behavior.
| Root Kiulu controller | +0x10001000+, IRQ 1 | Virtio-MMIO version 2 block device.
| Vihta interrupt controller | +0x0c000000+ | PLIC priority, enable, threshold, claim/complete.
| Virtio identity | Magic +0x74726976+, version 2, device 2, vendor +0x554d4551+ | Match the actual checks in the pinned driver, despite Finnish display names.
| Disk geometry | 512-byte device sectors; 1024-byte xv6 blocks | Keep the two units distinct throughout DMA, images, and drivers.
| Initial hart count | 1 | Upstream defaults to 3; record this deliberate bring-up configuration.
|===

The LP64D/RISC-V psABI target has 32-bit +int+, 64-bit +long+ and pointers,
little-endian objects, unsigned plain +char+, 16-byte stack alignment, and
the specified integer/floating argument conventions. Standard +long double+
is binary128 with size/alignment 16; it must not silently inherit SC-16's
binary64 representation. Unsupported long-double operations may remain
diagnosed until the broader conformance milestone, not falsely advertised.

*Dependencies:* <<nx-c90-initializers>>, <<nx-c90-qualifiers>>. +
*Acceptance:* Assert exact little-endian object bytes, neighboring bits,
single lvalue evaluation, promotion/conversion results, and volatile access
counts. Invalid types/widths, address-taking, and +sizeof+ of a bit-field diagnose.

** [ ] [[nx-c90-preprocessor]] *P2 / Complete C90 preprocessing and translation phases.*
   Audit trigraph/splice/token order, macro prescan, stringification, pasting,
   rescanning, +defined+, conditionals, includes, predefined values,
   +#line+, +#error+, +#pragma+, null directives, and diagnostic locations.
+
*Components:* shared Rust preprocessor/lexer and standalone fixtures. +
*Dependencies:* <<nx-compiler-boundaries>>. +
*Acceptance:* Independent preprocessing-only fixtures cover active/inactive
directives, include order, line/file mapping, integer expressions, and
recursive expansion. C90 and GNU/xv6 modes have explicit extension policies.

** [ ] [[nx-c90-limits]] *P2 / Verify every required translation minimum.*
   Audit identifiers, nested blocks/declarations, parameters/arguments,
   macros/includes, expressions, strings, records, objects, and source lines.
+
*Components:* compiler/preprocessor limits and resource diagnostics. +
*Dependencies:* <<nx-c90-declarators>>, <<nx-c90-preprocessor>>. +
*Acceptance:* Test at and immediately beyond each documented minimum/limit.
Historical 65,535-byte object and preprocessor boundary tests do not stand
in for the complete standard limit inventory.

** [ ] [[nx-c90-headers]] *P2 / Complete required C90 headers.*
   Audit +assert.h+, +ctype.h+, +errno.h+, +float.h+, +limits.h+,
   +locale.h+, +math.h+, +setjmp.h+, +signal.h+, +stdarg.h+, +stddef.h+,
   +stdio.h+, +stdlib.h+, +string.h+, and +time.h+ declarations/macros/types.
+
*Components:* target-selected guest headers and header tests. +
*Dependencies:* <<nx-guest-libc>>, <<nx-c90-numerics>>, <<nx-c90-preprocessor>>. +
*Acceptance:* Standalone, permitted repeat inclusion, and varied include
orders work with correct target values/types. Resolve conflicting historical
+setjmp+/+signal+ claims through execution; header smoke tests alone do not
establish the corresponding library behavior.

** [ ] [[nx-c90-hosted]] *P2 / Specify and implement hosted execution semantics.*
   Complete stream/device mapping, buffering, file operations, pushback,
   EOF/error state, temporary files, environment/command behavior, and
   termination/status on guest OS services rather than folder-disk host syscalls.
+
*Components:* application libc, xv6 services and hosted capability documentation. +
*Dependencies:* <<nx-c90-headers>>, <<nx-fs-compatibility>>. +
*Acceptance:* Test available/unavailable resources and all documented
stream/process outcomes, including errors. Standard interfaces remain distinct
from machine/game extensions; a documented unsupported requirement still
blocks a full hosted-conformance claim.

** [ ] [[nx-c90-library]] *P2 / Complete the required library functions.*
   Finish math, stdio, signal, stdlib, string, time/locale, and remaining
   facilities; validate setjmp/longjmp and signal-handler behavior separately.
   Specify domains, ranges, accuracy, boundaries, +errno+, and resource limits.
+
*Components:* guest libc/math runtime and execution tests. +
*Dependencies:* <<nx-c90-hosted>>, <<nx-c90-numerics>>. +
*Acceptance:* Independently checked results and failure cases cover each
required function/macro. Screen/graphics routines do not substitute for
standard C interfaces; approximate binary16 math cannot pass as C90 +double+.

** [ ] [[nx-c90-abi]] *P2 / Validate the complete C-visible ABI.*
   Cover scalar/aggregate representations, alignment, pointer/qualifier
   conversions, bit-fields, stack frames, calling conventions, and control flow.
+
*Components:* target ABI tests, compiler/assembler/execution integration. +
*Dependencies:* <<nx-c90-numerics>>, <<nx-c90-bitfields>>, <<nx-c90-linkage>>. +
*Acceptance:* Independent memory/call fixtures execute on every supported
Rust execution path. Update ABI capability claims only from results,
including floating arguments/returns and variadic/default promotions.

** [ ] [[nx-c90-independent]] *P2 / Integrate an independent conformance suite.*
   Review licensing and harness requirements; keep tests independent of
   compiler internals and preserve categorized output.
+
*Components:* Rust test runner, licensed external corpus integration. +
*Dependencies:* <<nx-toolchain-validation>>. +
*Acceptance:* A repeatable runner executes the selected corpus on Kiuas16,
accounts for its test inventory, and distinguishes harness failure, timeout,
unsupported cases, and actual semantic failures.

** [ ] [[nx-c90-conformance]] *P2 / Resolve independent conformance findings.*
   Exercise language, ABI, preprocessing, limits, and hosted facilities.
   Classify defects, implementation-defined/unspecified behavior, unsupported
   requirements, and invalid test assumptions without discarding failures.
+
*Components:* conformance results, compiler/runtime regressions, target docs. +
*Dependencies:* <<nx-c90-abi>>, <<nx-c90-limits>>, <<nx-c90-library>>, <<nx-c90-independent>>. +
*Acceptance:* Defects have fixes and behavioral regressions; classifications
are justified and repeatable. Unsupported required features remain visible
and prevent certification.

** [ ] [[nx-c90-release]] *P2 / Close the C90 compatibility release gate.*
   Run repository and independent suites and reconcile all capability claims.
+
*Components:* compiler/ABI/library documentation and release validation. +
*Dependencies:* <<nx-c90-conformance>>. +
*Acceptance:* Required language constraints, ranges/precision, ABI, headers,
library, translation limits, and supported execution paths pass with
independent evidence. Only then remove the nonconformance disclaimer.

legacy/current/target claims cannot be confused. Remove stale statements,
broken links, and duplicate task lists without discarding useful historical

** [ ] [[nx-workflow]] *P1 / Wire every supported host/developer surface.*

** [ ] [[nx-validation-ci]] *P0 / Automate deterministic execution gates.*

*Components:* Rust tests, CI configuration, fixture/result handling. +
*Dependencies:* <<nx-baseline>>, <<nx-toolchain-validation>>, <<nx-xv6-usertests>>. +

** [ ] [[nx-computer-release]] *P1 / Prove the complete-computer target.*
   Produce a reproducible release with source/provenance, boot/root images,

success/error/reset/IRQ/protection gates, filesystem persistence, and

** [ ] [[nx-multicore]] *P2 / Add and verify multiple harts.*

** [ ] [[nx-browser-portability]] *P2 / Validate any advertised browser target.*
   Audit rendering, storage persistence, audio/input permissions, networking,

*Components:* browser/host adapters, packaging and platform documentation. +
*Dependencies:* <<nx-computer-release>>. +

matrix and reports unavailable facilities explicitly. A wasm compile alone
does not establish a standalone browser release.

== Release evidence and source references

The P0 gate is <<nx-stage-5>> with its completed toolchain, hardware, and
firmware prerequisites. The P1 complete-computer gate is
<<nx-computer-release>>. Full C90 is a separate <<nx-c90-release>> gate;
SMP/browser claims require their own follow-on results.

Every advertised device requires success, error, reset, interrupt where
applicable, and protection tests. Every active application requires the
shared Phase 8 gate and its individual scenario. Keep disposable test images
separate from user disks and preserve original data on failed builds/installs.
