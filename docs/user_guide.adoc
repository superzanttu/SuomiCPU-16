= SC-16 Assembler and Emulator User Guide

== 1. Overview

SuomiCPU-16 is implemented in Rust. SC-16 is a small, byte-addressed machine with
eight general-purpose registers and a 16-bit instruction format. Assembly source
files use the +.asm+ extension. The assembler converts instructions to machine
code and places instructions or data at the addresses specified in the source.

The emulator loads the required guest-resident +firmware/bios.bin+ before launching a
program. The emulator always counts +firmware/bios.bin+ as trusted firmware and runs
it in kernel (Supervisor) mode. This is a trust-policy assumption, not a signature
check or secure-boot guarantee. The BIOS presents a classic text-mode setup
screen in the main window with a blue background, cyan headings, and highlighted
selection text. It discovers folder disks under
+disks/+ and loads a prebuilt
boot image after validating the selected disk's +disk.json+. Exactly one of
+kernel.bin+ (KERNEL mode) or +main.bin+ (USER mode) must exist; both or
neither reports +NOT_BOOT+. Metadata cannot override the executable or mode.
The selector uses +config/bios.json+ to remember the preferred
disk, startup behavior, and an editable 1-16 character SC-NET node ID. When
not configured, the BIOS generates a full-length +SC16-+ name with a random
hexadecimal suffix. This identifies the emulator to SC-NET only; guest
applications use their own network titles. Use Up/Down to select a setting.
Left/Right changes the boot device, or toggles a BOOL while its setting is
being edited. Enter on Boot Device saves the selection and starts that device;
Enter on another setting begins editing it directly in the main list. Type to
edit STRING and NUMBER values. Enter confirms an edit and Escape cancels it.
Changes to other settings must be saved with F10 before booting. Disk details
are clipped to one display row so long names do not wrap. F9 reloads
+config/bios.json+, and F10 saves it. Unsaved changes are shown as a warning and
prevent booting until saved. BOOL values are Yes/No, STRING values
are limited to 16 printable ASCII characters, and NUMBER values are signed
integers. Up to eight named custom settings from +config/bios.json+ appear in the
list and can be edited with the same controls. When automatic startup of a
preferred disk is enabled, the BIOS waits five seconds before booting and
shows a prompt; press Space during the countdown to enter setup instead.
Once started, CPU
reset begins execution at the loaded image's entry point. The first instruction
in the source determines that entry point, regardless of the numeric order of
the image's memory segments.

== 2. Running the emulator

Build and run an image from the repository root:

[source,console]
----
cargo run --bin sc16build -- examples/example.asm example.sc16img
cargo run --bin suomicpu16 -- example.sc16img
----

On Windows, run the PowerShell launcher with a source or binary path:

[source,powershell]
----
.\run.ps1 .\examples\example.asm
----

+run.ps1+ changes to the repository directory and starts the Rust emulator
through Cargo. C and assembly source paths are compiled to a temporary
+SC16IMG2+ image by +sc16build+ before the emulator starts; the temporary image
is removed when it exits. The runtime itself accepts only prebuilt images or
validated disk folders and does not compile or assemble source. The launcher
requires Rust and Cargo to be available on +PATH+. The Rust C
subset handles multiple +int+ functions with up to three parameters and local
+int+ variables, assignments, arithmetic/bitwise/shift/logical and signed comparison
expressions, conditional expressions, nested blocks, +if+/+else+, and
+while+/+do+/+for+ loops with +break+ and +continue+, including recursion.
Other C programs are rejected until their required features are ported. At
startup without an explicit program path, the BIOS displays the settings list
and available ID-named disk directories in stable order. Use Up/Down to select
a row and Enter to edit or boot. Invalid metadata, invalid images, and
+NOT_BOOT+ errors are logged; the BIOS remains available to retry another
disk. Close and relaunch the emulator to start a fresh BIOS session. The
emulator requires the shared
+firmware/bios.bin+ and displays a BIOS startup error if it is missing or invalid.
Build/install one catalog entry with +sc16build build-program <slug>+ or
+sc16build install-program <slug>+, or all entries with +build-programs+ and
+install-programs+. See link:programs.adoc[the program workflow] for manifests,
disk-name migration, and updates preserving local data. One-off
+sc16build package-disk+ still refuses an existing destination.
See +sc16_disk_format.adoc+ for the disk manifest and image requirements.
Build the shared BIOS image offline with
+cargo run --bin sc16build -- build-bios+; validate that
all program recipes still compile with
+cargo run --bin sc16build -- build-programs+. Builds write only
+build/programs/<slug>/+; installation stages and validates updates before
switching the disk directory.
Offline images use the version 2 +SC16IMG2+ container, with fixed load
addresses, an executable entry point, and explicit segment alignment and
permissions. +sc16asm+ and +sc16build+ emit this format; the loader rejects
older +SC16IMG1+ files. Generated images currently mark segments readable,
writable, and executable because code and mutable data may share a segment.
The MMU enforces mapped permissions when translation is enabled, but the
normal BIOS USER boot path does not yet enable translation and is not an
isolation boundary.
The game fills the emulator's main window after BIOS startup. The optional
80×25 *Bug Monitor* runs in a separate window and displays emulator logs and
dedicated guest diagnostic output. The *BUG MONITOR* toolbar button opens it;
its *CLOSE MONITOR* button hides it without changing guest execution.
Close the emulator with the window close button or Escape. Select text and press Ctrl+C to copy it;
the *COPY* button copies selected text or the visible monitor screen. The Bug
Monitor keeps a 1,000-row scrollback buffer, navigated with the mouse wheel.
Press F2 to hide/show the Bug Monitor. There are no host pause, stop, reset,
or reboot controls, and F1/F3/F4/F5 are not reserved host shortcuts.
Restart the emulator process for a fresh boot; build firmware offline before
launching if its source changed. F11 toggles fullscreen and windowed game
display. Start in fullscreen with
+cargo run -- --fullscreen+ or
+.\run.ps1 -Fullscreen+.

Additional examples are in link:../examples/commands.asm[+examples/commands.asm+]
and link:../examples/directives.asm[+examples/directives.asm+]:

[source,console]
----
cargo run --bin sc16build -- examples/commands.asm commands.sc16img
cargo run --bin suomicpu16 -- commands.sc16img
cargo run --bin sc16build -- examples/directives.asm directives.sc16img
cargo run --bin suomicpu16 -- directives.sc16img
----

The link:../examples/minimal_kernel.asm[+examples/minimal_kernel.asm+] example
builds a protected kernel disk that installs the IDT, enables the PIT and MMU,
starts a scheduled user task, and exits through the syscall ABI:
its page tables are static image data, so it is a boot-path fixture rather than
a general-purpose kernel.

[source,console]
----
cargo run --bin sc16build -- package-disk examples/minimal_kernel.asm disks/KERN0001 MinimalKernel 65536 --kernel
cargo run --bin suomicpu16
----

The link:../examples/syscall_kernel.asm[+examples/syscall_kernel.asm+] and
link:../examples/syscall_child.asm[+examples/syscall_child.asm+] examples
exercise the syscall lifecycle from user programs. The kernel spawns the child,
yields, sleeps, waits for its exit status, and exits with that status. The child
first attempts a supervisor-only read; the sample handler skips that faulting
instruction to demonstrate isolation. It allocates a page with +sys_mmap+ for
its file buffer, then reads +input.txt+, writes its contents to the console and
+result.txt+, and exits. This simple recovery policy and the kernel's lack of a
guest-written frame allocator make it a verification fixture, not a
general-purpose operating system. The syscall fixture builds its initial page
tables during guest startup; +minimal_kernel.asm+ keeps static tables for the
smaller boot-path example.

[source,console]
----
cargo run --bin sc16build -- package-disk examples/syscall_kernel.asm disks/KERN0002 SyscallKernel 65536 --kernel
cargo run --bin sc16build -- examples/syscall_child.asm target/syscall_child.img
Copy-Item target\syscall_child.img disks\KERN0002\child.bin
Set-Content -NoNewline -Encoding ascii disks\KERN0002\input.txt hello
cargo run --bin suomicpu16
----

The Rust C compiler used by the offline build tool supports a limited subset:
multiple +int+ functions
and +void+ helper functions with up to three parameters, local +int+ variables,
initialized and zero-initialized global +int+ variables and arrays, brace-
initialized integer globals and arrays, and indexed access to global integer
arrays. Translation-unit enum constants and enum-typed integer declarations
and scalar integer typedef aliases are also supported. It also supports
object-like +#define+ macros and +#undef+, assignments, arithmetic,
bitwise/shift/logical and
prefix/postfix increment and decrement, signed comparison, conditional, and
comma expressions, nested blocks,
+if+/+else+,
+switch+/+case+/+default+ with fallthrough, +goto+ labels, +while+, +do+/+while+,
basic integer +sizeof+, and +for+ loops with +break+ and +continue+, including
recursion.
Programs outside this subset are rejected with a Rust compiler diagnostic.
Only object-like macros and +#undef+ are preprocessed;
+#if+/+#elif+ integer constant expressions and +#ifdef+/+#ifndef+ conditional
branches are supported. Backslash-newline source continuations are spliced
before preprocessing and tokenizing. Quoted includes search beside the
including source; angle-bracket includes search the repository +toolchain/include/+ directory.
Function-like macros support argument substitution, stringification, and token
pasting; variadic macros remain unsupported. The Rust C frontend also supports
console +fgets+, +puts+, and a restricted +printf+ format subset: literal text,
+%%+, and at most one +%s+ argument. Other +printf+ conversions remain
unsupported. Compile C sources to segmented images with the Rust build tool:

[source,console]
----
cargo run --bin sc16build -- examples/example.asm build/example.sc16img
cargo run --bin suomicpu16 -- build/example.sc16img
cargo run --bin sc16build -- examples/factorial.c examples/factorial.sc16img
cargo run --bin suomicpu16 -- examples/factorial.bin
----

The runtime accepts prebuilt flat +.bin+, +SC16IMG2+ images with +.img+ or
+.sc16img+ extensions, and validated folder disks. Source files must be built
offline with +sc16build+ (or by +run.ps1+ before the emulator starts). A
+.bin+ file starting with the +SC16IMG2+ signature is read as an image
container; the replaced +SC16IMG1+ signature is rejected rather than executed
as flat code.

The input file argument is optional. Without it, the BIOS loads a prebuilt
image from a selected folder disk. Use +--disk ID+ to preselect a boot disk
in BIOS, or to mount that folder filesystem with an explicit prebuilt image.
The Rust emulator uses
Macroquad for its window, display, and input.

== 3. Assembly source syntax

* Mnemonics and directives are case-insensitive. Register names are +R0+ through
  +R7+.
* Labels start with a letter or underscore and may then contain letters, digits,
  and underscores. Labels are case-sensitive and end in a colon:

[source,asm]
----
  loop:
      INC R0
      JMP loop
----

* A label can share a line with an instruction or directive:

[source,asm]
----
  message: .data string "Hello"
----

* +;+ and +#+ start comments outside quoted strings.
* Integer instruction operands accept decimal (+25+), hexadecimal (+0x19+),
  octal (+0o31+), and binary (+0b11001+) notation.
* There is no implicit +CALL+, +RET+, +NOP+, expression evaluation, or data
  alignment directive. Base instructions occupy two bytes; extended
  instructions use two, four, or six bytes depending on their operands.

== 4. Directives

=== +.address+

Set the current *byte address* for subsequent instructions, data, and labels:

[source,asm]
----
.address 0x0100
entry:
    LDI R0, 25
    HALT

.address 0x0200
scratch:
    .data hex 00, 00, 00
----

Use as many +.address+ directives as needed. Each takes one numeric address;
labels are not accepted as +.address+ arguments. Moving the address does not
emit bytes. Sections need not be written in address order. The assembler returns
separate memory segments for disjoint ranges and rejects overlapping output.

Valid addresses are +0+ through +0x3FFFFFFF+, the emulator's 1 GiB memory
range.
The entry point is the address of the first instruction encountered in source
order. If there are no instructions, it is the first emitted data address; if
the source emits nothing, it is the initial address +0+.

=== +.data+

Emit one or more bytes at the current address. Each numeric value must fit in a
byte (+0x00+ through +0xFF+). Values can be separated by spaces or commas.

==== Hexadecimal

The +hex+ format treats unprefixed tokens as hexadecimal. An optional +0x+
prefix is allowed:

[source,asm]
----
.data hex 53, 0x43, FF
----

This emits bytes +0x53+, +0x43+, and +0xFF+.

==== Octal

The +oct+ format treats unprefixed tokens as octal. An optional +0o+ prefix is
allowed:

[source,asm]
----
.data oct 123, 0o377
----

This emits bytes +0x53+ and +0xFF+.

==== Binary

The +bin+ format treats unprefixed tokens as binary. An optional +0b+ prefix is
allowed:

[source,asm]
----
.data bin 01010011, 0b01000011
----

This emits bytes +0x53+ and +0x43+.

==== Strings

The +string+ format accepts one or more quoted strings. Strings are encoded as
UTF-8 and emitted exactly as given; no null terminator is added. Quoted escapes
such as +\n+ and +\t+ are interpreted:

[source,asm]
----
.data string "Hello", " world!\n"
----

This emits the UTF-8 bytes of +Hello world!+ followed by a newline byte.

=== +.include+

Insert another assembler source file at the current point:

[source,asm]
----
.include "firmware/fonts/font5x7.asm"
----

The path is relative to the file containing the +.include+, so the same include
works when the top-level source is assembled from another working directory.
Included sources are assembled inline: their +.address+ directives change the
current address, and their labels share the global label namespace with the
including source. Nested includes are supported. Circular includes, missing
files, and invalid paths are reported as assembly errors. Use unique labels in
shared include files; including a file twice that defines the same label
produces a duplicate-label error.

== 5. Instruction reference

Base instructions occupy one 16-bit word (two bytes), stored most-significant
byte first. Extended instructions may use additional words as noted in their
descriptions. Registers are selected from +R0+ through +R7+. Unless stated
otherwise, instructions do not change the condition flags.

=== Program and immediate instructions

[cols="1,1,1"]
|===
|Instruction
|Syntax
|Operation

|+HALT+
|+HALT+
|Stop execution.

|+LDI+
|+LDI Rd, value+
|Load an immediate value into +Rd+. Values from +0+ to +255+ use one word. Values from +256+ to +65535+ expand to +LDI+ (low byte) followed by +LDI_H+ (high byte).

|+LDI_H+
|+LDI_H Rd, high_byte+
|Replace the high byte of +Rd+, preserving its low byte. +high_byte+ must be +0+ to +255+.

|+LDI30+
|+LDI30 Rd, address+
|Load a full 30-bit address (+0+ through +0x3FFFFFFF+) into a register. +LDI19+ and +LDA+ are compatibility aliases.
|===

For example:

[source,asm]
----
LDI R0, 0x34
LDI_H R0, 0x12       ; R0 becomes 0x1234
; Equivalent one-line pseudo-instruction:
LDI R1, 0x1234
----

The assembler accepts +LDI R1, 0x1234+ as a pseudo-instruction and emits the
same pair of machine instructions.

=== Memory and register instructions

[cols="1,1,1"]
|===
|Instruction
|Syntax
|Operation

|+LD+
|+LD Rd, Ra+
|Load one byte from the address in +Ra+ into +Rd+.

|+ST+
|+ST Ra, Rs+
|Store the low byte of +Rs+ at the address in +Ra+.

|+LDW+
|+LDW Rd, Ra+
|Load a big-endian 16-bit word from the address in +Ra+.

|+STW+
|+STW Ra, Rs+
|Store a big-endian 16-bit word from +Rs+ at the address in +Ra+.

|+LDWS+
|+LDWS Rd, offset+
|Load a word from +SP \+ offset+; offset is 0-255.

|+STWS+
|+STWS Rs, offset+
|Store a word at +SP \+ offset+; offset is 0-255.

|+MOV+
|+MOV Rd, Rs+
|Copy the register value from +Rs+ to +Rd+.
|===

Example:

[source,asm]
----
LDI R0, 0x2000
LDI R1, 0x2A
ST R0, R1
LD R2, R0
MOV R3, R2
----

+LD+ and +ST+ access byte-sized memory. +ST+'s first operand is the address
register; its second operand is the value register.

=== Arithmetic and logic

[cols="1,1,1"]
|===
|Instruction
|Syntax
|Operation

|+ADD+
|+ADD Rd, Rs+
|+Rd = Rd \+ Rs+; sets +Z+ and +C+.

|+SUB+
|+SUB Rd, Rs+
|+Rd = Rd - Rs+; sets +Z+ and +C+.

|+AND+
|+AND Rd, Rs+
|+Rd = Rd & Rs+.

|+OR+
|+OR Rd, Rs+
|+Rd = Rd \| Rs+.

|+XOR+
|+XOR Rd, Rs+
|+Rd = Rd ^ Rs+.

|+NOT+
|+NOT Rd+ or +NOT Rd, Rs+
|+Rd = ~Rd+ or +Rd = ~Rs+, limited to the low eight bits.

|+INC+
|+INC Rd+
|Increment +Rd+ by one.

|+DEC+
|+DEC Rd+
|Decrement +Rd+ by one.

|+CMP+
|+CMP Ra, Rb+
|Set +Z+ and +C+ as if subtracting +Rb+ from +Ra+, without storing the result.

|+SHR+
|+SHR Rd+
|Logical right shift of the low 16 bits of +Rd+ by one.
|===

For two-register arithmetic/logical operations the first operand is also the
destination. +CMP+ uses its two operands only as inputs.

The original byte-oriented instructions retain their existing behavior:
register values use signed 64-bit host storage, +LDI+ may load up to 16 bits, arithmetic
does not automatically mask its result, and byte stores and +POP+ retain only a
byte. +SHR+ explicitly operates on a 16-bit word. The C compiler emits masks
where needed to implement its 16-bit integer semantics.

+ADD+ sets +Z+ when its result is zero and +C+ when the result exceeds +255+.
+SUB+ sets +Z+ when its result is zero and +C+ when the result is negative
(borrow). +CMP+ sets +Z+ when the operands are equal and +C+ when the first
operand is less than the second. +AND+, +OR+, +XOR+, +NOT+, +INC+, and +DEC+ do
not update the flags in the current emulator.

=== 32-bit register-pair arithmetic

+ADD32+, +SUB32+, +CMP32+, +AND32+, +OR32+, +XOR32+, +SHL32+, +LSR32+,
+ASR32+, +NEG32+, +MOV32+, +LD32+, +ST32+, +MUL32+, +DIV32+, +DIV32S+, +MOD32+,
and +MOD32S+ operate on adjacent register pairs. The even
register is the high 16 bits and the following odd register is the low 16 bits:
for example, +R0+ names the +R0:R1+ pair and +R2+ names +R2:R3+. Binary
arithmetic/logic operations and +MOV32+ require even pair registers. Shift
counts may be an immediate from 0 to 31 or the low five bits of a register.
+LD32 Rd, Ra+ loads four big-endian bytes at the 30-bit address in pair +Ra+
into pair +Rd+; +ST32 Rs, Ra+ stores the value in pair +Rs+ there. Both
register-pair operands must start at an even register. Memory access wraps at
the end of the 1 GiB address space and follows normal memory-mapped-device
read/write behavior.
+MUL32+ writes the low 32 product bits; it sets +C+ for unsigned overflow and
+V+ for signed overflow. +DIV32+/+MOD32+ are unsigned; the +S+ forms are signed,
with division truncated toward zero and remainder following the dividend.
Division by zero yields zero for quotient or the dividend for remainder and
sets +C+; nonzero divisors clear +C+. These arithmetic instructions set +Z+
and +N+ from the result.

+ADD32+/+SUB32+ set +Z+, +N+, +C+ and +V+ for 32-bit arithmetic; +CMP32+ sets
the same flags without changing its destination. +AND32+/+OR32+/+XOR32+ set
+Z+ and +N+ and clear +C+ and +V+. Shifts set +Z+, +N+, and +C+ (the last bit
shifted out) and clear +V+. A zero-count shift preserves +C+. +NEG32+ sets
+Z+, +N+, +C+ (nonzero input), and +V+ (the signed minimum value). +MOV32+
does not change flags.

These instructions use the extended +0x1A+ selector in the +OP_SHR+ space and
are implemented by the Rust CPU. The
+MOVSPH+ miscellaneous instruction reads the high 14
bits of the 30-bit stack pointer; together with +MOVSP+, it lets compiler code
form full stack addresses for 32-bit objects. +SETSPH+ sets those upper bits
without disturbing the low 16-bit offset, allowing code to restore a full
30-bit stack position.

Encoding: word 1 is +0xF800 | (high-register << 8) | 0x1A+; word 2 is
+(operation << 12) | (immediate flag 0x0800) | source/count+. Operation codes
are +ADD32+=0, +SUB32+=1, +CMP32+=2, +AND32+=3, +OR32+=4, +XOR32+=5,
+SHL32+=6, +LSR32+=7, +ASR32+=8, +NEG32+=9, and +MOV32+=10. Shift immediates
use the low five bits and the immediate flag; register shift counts use the
low five bits of the selected register. +LD32+=11 and +ST32+=12. The group occupies the previously
unused +0x1A+ selector, distinct from the existing +0x1B+-+0x1F+ extensions.
+MUL32+=13, +DIV32+/+DIV32S+=14, and +MOD32+/+MOD32S+=15. The signed +S+
forms set the immediate/modifier flag in word 2; division and remainder
operands otherwise use an even source register pair.

=== Integer multiply and divide

[cols="1,1,1"]
|===
|Instruction
|Syntax
|Operation

|+MUL+
|+MUL Rd, Rs+ / +MUL Rd, imm+
|+Rd+ = low 16 bits of +Rd * source+; +C+ is set if the product exceeds 16 bits.

|+MULHU+
|+MULHU Rd, Rs+ / +imm+
|+Rd+ = high 16 bits of the unsigned 32-bit product.

|+MULHS+
|+MULHS Rd, Rs+ / +imm+
|+Rd+ = high 16 bits of the signed 32-bit product.

|+DIV+
|+DIV Rd, Rs+ / +imm+
|+Rd = Rd / source+, unsigned.

|+DIVS+
|+DIVS Rd, Rs+ / +imm+
|+Rd = Rd / source+, signed, truncating toward zero.

|+MOD+
|+MOD Rd, Rs+ / +imm+
|+Rd = Rd % source+, unsigned.

|+MODS+
|+MODS Rd, Rs+ / +imm+
|+Rd = Rd % source+, signed; the sign follows the dividend.
|===

The source is a register (+R0+-+R7+) or a 16-bit immediate (decimal, +0x+ hex,
or negative). Operands are taken as 16-bit values and the result is always a
clean 16-bit value. +Z+ is set when the result is zero. Dividing by zero gives a
quotient of +0+ or a remainder equal to the dividend, and sets +C+; otherwise
the division instructions clear +C+.

Encoding: these share the +0x1F+ opcode with the extension group. The first
word is +0xF800 | (Rd << 8) | 0x1E+; the second word is
+(operation << 12) | (immediate flag 0x0800) | Rs+ with operations
+MUL+=0, +MULHU+=1, +MULHS+=2, +DIV+=3, +DIVS+=4, +MOD+=5, +MODS+=6. With an
immediate, a third word holds the 16-bit value. The register form is four
bytes and the immediate form six bytes. The C compiler emits +MUL+, +DIV+/+DIVS+
and +MOD+/+MODS+ directly for +*+, +/+ and +%+; there are no software routines.

=== IEEE-754 floating-point instructions

The +F32+ and +F64+ instruction families operate on IEEE-754 binary32 and
binary64 values. Binary32 values use an even register pair (+R0:R1+, +R2:R3+,
+R4:R5+, or +R6:R7+), with the most-significant word first. Binary64 values
use +R0:R1:R2:R3+ or +R4:R5:R6:R7+, also most-significant word first.
Arithmetic instructions replace the destination value with the result:

[cols="1,1,1"]
|===
|Instruction family
|Examples
|Operation

|Arithmetic
|+F32ADD+, +F32SUB+, +F32MUL+, +F32DIV+; corresponding +F64+ forms
|Add, subtract, multiply, divide

|Compare
|+F32CMP+, +F64CMP+
|Set +Z+ for ordered equality and +C+ for ordered less-than; unordered comparisons clear both

|Integer conversion
|+I16TOF32+, +U16TOF32+, +I32TOF64+, +F64TOU32+
|Convert between signed/unsigned 16/32-bit integers and the indicated floating format

|Format conversion
|+F32TOF64+, +F64TOF32+
|Convert between binary32 and binary64

|Unary
|+F32NEG+, +F64NEG+, +F32SQRT+, +F64SQRT+
|Negate or calculate square root
|===

Conversions from floating point to integers truncate toward zero. For non-finite
values the conversion instructions produce zero; finite values outside the
destination range produce the low destination bits. C programs must not depend
on those results for out-of-range conversions, whose result is undefined by
C90. Operations round to nearest, ties to even; subnormals and signed zero are
supported. Overflow produces infinity and invalid operations produce a
canonical quiet NaN.

These are assembler/emulator instructions; the C compiler has not yet been
updated to emit them. In compiled C, +float+, +double+, and +long double+
currently remain binary16 values stored in two bytes. See
link:c90_target_abi.adoc[+c90_target_abi.adoc+] for the selected future C ABI
and the remaining compiler/backend work.

Every branch also has an +X+ spelling (+BLTX+, ...); all conditional branches

containing target bits 29-16 and a word containing bits 15-0. Far conditional
branches use prefix +0xF80D+ for the condition, followed by the same two target

[source,asm]

+JMP+, +BZ+, +BC+, and +CALL+ encode an 11-bit address (+0+ to +0x7FF+); +JZ+
encodes an 8-bit target (+0+ to +0xFF+). These are absolute *byte* addresses,
not instruction indexes or offsets. +JZ+ tests the named register directly; it
does not test the +Z+ flag. +BZ+ and +BC+ test the +Z+ and +C+ flags,
respectively, commonly after +SUB+ or +CMP+.
+JMPX+, +BZX+, +BCX+, and +CALLX+ use six bytes and encode a full 30-bit address;
use them when code or routines are outside the short-address range.
All +CALL+, +CALLX+, +CALLR+, and +CALLRP+ instructions push the following
30-bit PC as four big-endian bytes; +RET+ restores all 30 bits. +CALLRP+ uses
the register-pair layout for machine addresses: low 16 address bits in +Rlow+
and high 14 bits in +Rhigh+.

The compact far-control prefix word uses bits 10-9 for the operation and fixed
selector +0x3E+ in bits 5-0; its next two words contain address bits 29-16 and
15-0. Far conditional branches use bits 10-7 for the condition code and fixed
selector +0xD+ in bits 3-0; their next two words contain the same address
fields. Both encodings therefore cover the full 1 GiB address space in six
bytes.

=== Stack and interrupt instructions

[cols="1,1,1"]
|===
|Instruction
|Syntax
|Operation

|+PUSH+

|Push a 16-bit register value to the stack.

|+POP+
|+POP Rd+
|Pop a value from the stack into +Rd+; the register is masked to one byte.

|+EI+
|+EI+
|Set the interrupt-enable bit in the interrupt control register.

|+DI+

|Clear the interrupt-enable bit.

The stack pointer starts at +0x3FFFFFFF+. +PUSH+ decrements the pointer by two and
stores a big-endian word; +POP+ reads that word and advances the pointer by two.
+CALL+/+RET+ use the same stack. The +POP+ instruction loads only the low byte
into a general-purpose register, whereas +RET+ and +RTI+ use the full popped
word. +LDW+/+STW+ use big-endian byte order. +LDWS+/+STWS+ address words from
the current stack pointer; +ADJSP+ reserves or releases a small stack region.
On interrupt entry, the CPU pushes the 30-bit return PC and all four condition
flags (+Z+, +C+, +N+, and +V+) onto the current stack. +RTI+ restores them.
The interrupt vectors are four-byte, big-endian addresses at +0x0002+
(keyboard), +0x0006+ (RTC), and +0x000A+ (instruction timer).

Example vector setup:

[source,asm]
----
.address 0x0002
.data hex 00, 00, 00, 70
.address 0x0006
.data hex 00, 00, 00, 70
.address 0x000a
.data hex 00, 00, 00, 70
.address 0x0070
interrupt_handler:
    RTI
----

The interrupt control register (+ICR+, +0x43002+) uses bit 0 as the global
interrupt enable, bit 1 as keyboard-pending, bit 3 as RTC-pending, and bit 4
as instruction-timer-pending. The CPU services one pending source after each
instruction, in keyboard, timer, RTC priority order. It clears only the source
being serviced; other pending sources remain set. A pending bit coalesces
repeated events of the same source until serviced.

The 16-bit instruction-timer period is stored big-endian at +0x4301e+-+0x4301f+.
Writing zero disables it; a nonzero period raises the timer interrupt every
that many executed instructions and writing a new period restarts its countdown.
The timer is independent of rendering and also runs during headless execution.
The RTC still raises its interrupt on display-loop updates. Set up vectors and
handlers before enabling interrupts.

=== Multitasking model

The instruction timer and interrupt-return frame make preemptive software task
switching possible. An interrupt frame saves the PC and flags, but not the
general registers or stack pointer. A scheduler handler must first save every
general register it will modify, save the resulting stack pointer in the
current task's control block, load the next task's saved stack pointer, restore
that task's registers, and finish with +RTI+. A task's saved stack must include
its suspended interrupt frame so +RTI+ resumes its own PC and flags. Enable the
timer and global interrupts only after all task stacks, vectors, and scheduler
state are initialized.

SC-16 currently has one shared, writable address space and no user/supervisor
modes, memory protection, or hardware task contexts. Such an OS can schedule
cooperating tasks, but tasks are not isolated from one another or from the
kernel; scheduling and register preservation are software responsibilities.

== 6. Instruction encoding and execution

* Memory is byte-addressed. The PC points to a byte address and advances by two
  for each 16-bit instruction.
* The instruction word has a five-bit opcode in bits 15-11. Other bits hold a
  destination register, source registers, or an immediate/address field,
  depending on the instruction.
* Instruction words are stored big-endian: the high byte is at the instruction
  address and the low byte is at the next address.
* The assembler's +.data+ directives emit literal bytes and do not apply
  instruction endianness or alignment.
* There is no ROM protection: assembled segments are copied into the same
  writable memory used by the CPU.

== 7. Emulator memory and devices

The backing memory is +2**30+ bytes (+0x40000000+, or 1 GiB). CPU read/write
addresses are masked with +0x3FFFFFFF+, so out-of-range accesses wrap into that
memory. Program-image loading is stricter and rejects segments that extend past
the end of the backing memory. The map below lists reserved low-memory and
device ranges; other addresses are ordinary RAM. The process stack starts at
the final valid address and grows downward.

The display supports 320x240 indexed 8-bit mode and 640x480 packed 4-bit mode.

+0x50000 \+ y * 320 \+ x+. At 640x480, two pixels share a byte (left pixel in
the high nibble, right pixel in the low nibble), using palette indices 0-15.
The 256-entry palette names colors 0-11; index 25 is pure blue in 320x240 mode.
Direct CPU writes update background layer 0, shown at the next display refresh.
No CPU-visible back buffer is reserved: compositing and the other four layers
are held in private GPU memory. The emulator executes up to 30,000 instructions
per display frame (capped at 60 frames per second), so long drawing routines can
finish without requiring a separate screen update for every CPU instruction.
When the CPU halts, the window remains open with the final frame displayed;
press any key to close it, or close the window using its title-bar control.
Keyboard key presses write the character byte to the keyboard address and mark
a keyboard interrupt pending. Reading the keyboard address returns and clears
the pending character. The RTC writes seconds, minutes, and hours to its three
declared byte addresses.

commands and C helpers defined in +toolchain/include/folder_fs.h+. It supports directory
listing, file reads and replacement writes, directory creation, deletion,
rename, and metadata queries. Paths are normalized relative to the mounted
folder disk; transfers are bounded and failures set an explicit status. See
+docs/sc16_disk_format.adoc+ for the request layout and access policies.

The former guest block interface is removed. Original JSON block-disk files
remain as import sources and can be converted with
+sc16build import-block-disk+. +programs/disk-editor/src/disk_editor.c+ is now a
USER-mode text-file editor for the mounted folder disk; it creates or updates
files up to 256 bytes and leaves protected files unchanged. Tank-16's
+toolchain/include/disk.h+ file-list helper retains recursive directory listing for legacy
program code; file reads use the folder-filesystem read command.

== 9. ANSI C90 compiler

The Rust C compiler is C90-oriented, **not a fully conforming ANSI/ISO C90
implementation**. It implements a subset of the language and common
preprocessing features, but some required
C90 constructs, target type requirements, and the standard library are not
implemented. Do not assume that a program accepted by another C90 compiler
will compile or have identical behavior on SC-16.

The ABI choices targeted for full conformance, including type representations,
pointer encoding, aggregate layout, and function-call conventions, are recorded
in link:c90_target_abi.adoc[+c90_target_abi.adoc+]. The document describes
the intended target and does not imply that the current compiler implements
those choices completely.

Supported language features include:

* File-scope and block-scope declarations; function prototypes, modern
  definitions (including definitions with omitted return type, which defaults
  to +int+), and identifier-list (old-style) definitions with pre-body
  parameter declarations (undeclared old-style parameters default to +int+);
  unspecified-parameter declarations using +f()+ distinct from no-argument
  prototypes using +f(void)+; recursion; and C90 declarations before statements
  within a block. Variadic prototypes and definitions accept calls with the
  required fixed arguments followed by additional arguments, applying the
  default promotions needed by the current target types. +<stdarg.h>+ provides
  +va_list+, +va_start+, +va_arg+, and +va_end+ for accessing variadic arguments.
* +typedef+ names, including one-dimensional array typedefs, enumerations,
  structure and union declarations, member access with +.+ and +->+, scalar and
  array initialization, and file-scope structures and arrays of structures
  initialized with nested braces and integer constant expressions (omitted
  members are zero-filled). C90 integer type specifiers include standalone
  +signed+ and +unsigned+;
  +char+ and +unsigned char+ operands receive integer promotions. Global
  pointer initializers accept null pointer constant expressions and the
  compiler's SC-16 hexadecimal address-constant extension. Redeclarations with
  incompatible function parameter types are diagnosed. Unary arithmetic,
  bitwise complement, and logical operators diagnose operands that do not meet
  their C90 type constraints.
* Bounded arrays, including multidimensional arrays and initialized arrays with
  an omitted outer bound,
  integer constant expression bounds (including arithmetic, enum constants,
  casts, +sizeof+ on complete object types, and conditional expressions), array parameters
  adjusted to pointers, pointers, casts, +sizeof+, and the comma and conditional
  operators.
* Blocks, expression statements, +if+/+else+, loops, +switch+ with integer
  constant-expression +case+ labels, +default+, +break+, +continue+, +goto+,
  labeled statements, and +return+; supported scalar arguments and return
  expressions are converted to their declared parameter or function return
  types, with incompatible pointer/scalar conversions rejected.
* Integer and floating constants, character constants, strings (including
  adjacent string-literal concatenation), assignment and compound assignment,
  increment/decrement, arithmetic, bitwise and shift operations, comparisons,
  and logical operators with short-circuit evaluation. Binary operators check
  arithmetic, integer, and scalar operand requirements and reject invalid
  pointer arithmetic and comparisons. Conditional and control-flow conditions
  must also be scalar expressions. Compound assignments use the corresponding
  arithmetic and pointer rules, including pointer scaling and floating
  conversions. Pointer subtraction returns an element difference rather than
  a byte difference. Arrays and enumerators are rejected as modifiable
  lvalues; compatible structure and union assignments copy the complete object
  representation, and fixed-parameter structure and union arguments are copied
  by value. Structure and union returns use caller-owned result storage and are
  tested with nested calls and recursion; members of a returned temporary are
  readable but are not modifiable lvalues. Duplicate storage-class
  specifiers and duplicate +const+/+volatile+ qualifiers are diagnosed.
  +const+ is enforced for supported non-pointer scalar and array objects,
  structure/union objects and members, including +typedef const+ aliases;
  initializers and reads remain supported. Whole-record assignment is rejected
  when the record contains a const-qualified member, while assignments to its
  other mutable members remain valid.
  Scalar initializers may use nested braces around exactly one value.
* Object-like and function-like macros, +#+, +##+, +defined+, conditional
  inclusion, +#include+, +#undef+, +#error+, +#pragma+, trigraph replacement,
  and backslash-newline splicing. Quoted includes are searched relative to the
  including file; angle-bracket includes are searched in the repository's
  +toolchain/include/+ directory.

The compiler's data model is target-specific and does *not* meet all the C90
minimum requirements:

* +int+ and +unsigned int+ are 16-bit; +char+ and +unsigned char+ occupy one
  byte. +short+ is 16-bit, and +long+/+unsigned long+ are 32-bit with the
  minimum ranges required by C90. The compiler implements pair-based storage,
  scalar arithmetic, +switch+, and function argument/return handling for these
  +long+ types. The compiler supports indirect 32-bit lvalues and 30-bit
  pointer address paths. Regression tests cover high-address byte, word,
  and +long+ accesses as well as indexed accesses across +0xFFFF+, but not every
  pointer conversion, arithmetic, alignment, or wraparound case. Integer
  literal types use the target's +int+, +unsigned int+, and 32-bit +long+
  candidate ranges. An explicit cast from a 32-bit integer to an object pointer
  uses its low 30 bits as the address; this is the target's implementation-
  defined conversion. For compatibility with existing programs, a file-scope
  pointer initializer also accepts an integer constant in the SC-16 30-bit
  address range as an implementation extension. Converting an object pointer
  to a 32-bit integer preserves its 30-bit address value; conversion to 16-bit
  +int+ preserves the low 16 bits. These pointer/integer conversions are
  implementation-defined.
* +float+, +double+, and +long double+ use the SC-16 IEEE-754 binary16 format.
  In particular, +double+ does not meet C90's required minimum range or
  precision.
* Object pointers occupy four bytes for the machine's 30-bit address space.
  Their in-memory representation stores the low 16 address bits first and the
  high 14 bits second, with each word in big-endian byte order.
  +size_t+ is unsigned 32-bit +long+, and +ptrdiff_t+ is signed 32-bit +long+;
  compatible object-pointer subtraction produces a signed 32-bit element
  difference. Pointer arithmetic and dereferencing have not yet been
  exhaustively checked for all address, alignment, and overflow cases.
  The ISA provides register-pair indirect control flow, but function-pointer
  declarators and general C function-pointer calls are not supported.
* +static+, +extern+, +auto+, +register+, and +volatile+ specifiers do not have
  their full C linkage, storage-duration, or volatile-access semantics.
  Block-scope +static+ and +extern+ declarations are diagnosed as unsupported;
  they are not treated as automatic locals.
  The address-of constraint is enforced for local objects declared +register+,
  and +auto+/+register+ file-scope declarations and storage classes on record
  members are diagnosed. Named +register+ parameters in supported prototypes
  and definitions also reject address-taking.
  One-level const-qualified pointer targets are supported for reads through
  local, global, and parameter pointers; writes and updates through them are
  rejected. Const-qualified scalar and bit-field record members support
  aggregate initialization, and writes to those members are rejected.
  Function declarations diagnose conflicting one-level pointer-target
  qualifications. Qualifier-dropping conversions between simple pointer
  variables, addresses of const objects, fixed pointer arguments, and pointer
  returns are diagnosed, including local pointer initializers and call
  arguments. Conditional and comma expressions, pointer casts, and direct
  function-call results are checked for qualifier loss and writes. Other
  expression paths and multi-level qualification remain incomplete. Qualifiers
  on pointer objects are diagnosed as unsupported instead of being silently
  discarded.
* Global/static storage begins at +0x80000+ (+GLOBAL_BASE+ in the Rust C
  compiler); uninitialized globals are zeroed. The current compiler allocates
  static data through +0xFFFFF+.
  Local variables, arguments, return addresses, and temporaries use the machine
  stack.

Important language gaps include multidimensional array function-parameter
declarators beyond the supported forms, function pointers, and parts of C90's
declarator, initializer, and
constant-expression rules. The preprocessor also does not implement every
translation-phase and directive semantic required for strict C90 conformance.
Numeric +#line+ directives remap subsequent diagnostic line numbers, including
preprocessor diagnostics. An optional filename remaps subsequent diagnostic
filenames and the value of +_FILE_+; without a filename, the current mapped
filename is retained.

The standard library remains incomplete and is not C90-conforming. Headers are
available for +<stddef.h>+, +<limits.h>+, +<float.h>+, +<ctype.h>+, +<errno.h>+,
+<assert.h>+, +<stdio.h>+, +<stdlib.h>+, +<string.h>+, +<stdarg.h>+,
+<locale.h>+, +<time.h>+, +<math.h>+, and +<setjmp.h>+. The SC-16
+setjmp+/+longjmp+ implementation saves a 30-bit continuation and stack pointer
in an 8-byte +jmp_buf+; +longjmp+ restores that context and converts a zero
value to one. +<signal.h>+
and signal-handler dispatch remain unimplemented. The C99 +<stdint.h>+ header
is an extension, not a C90 header.
The target has no 64-bit integer type. +<stddef.h>+ defines +size_t+,
+ptrdiff_t+, +wchar_t+, +NULL+, and +offsetof+; +size_t+ is a 32-bit unsigned
+long+ used for the target's 30-bit address range.

The string and memory routines, C-locale character routines, and several
+<stdlib.h>+ services are linked when referenced. These include integer and
decimal-string conversions, +div+/+ldiv+, random numbers, and a bounded
64-KiB heap for +malloc+, +calloc+, +realloc+, and +free+. Allocation failure
returns +NULL+ and reports +ENOMEM+; zero-size allocation returns +NULL+.
+qsort+ and +bsearch+ are unavailable because callback function pointers are
not supported. +exit(status)+ and +abort()+ halt the target; the emulator has
no host process exit-status channel and cannot perform +atexit+ callbacks or
stream cleanup. There is no target environment-variable store, so +getenv+
returns +NULL+; there is no command processor, so +system(NULL)+ returns zero
and commands return -1. +assert+ evaluates its expression once and halts on a
failed assertion unless +NDEBUG+ is defined.

+<stdio.h>+ maps +stdin+, +stdout+, and +stderr+ to the emulator's
non-seekable console. Character/string I/O, integer/text +printf+ formatting,
and common +scanf+ conversions are supported. Console input has no EOF
condition, and +feof+ therefore remains false. This runtime is unbuffered;
+setvbuf+ only accepts +_IONBF+. Hosted file operations (+fopen+, +remove+,
+rename+, and temporary files) fail with +ENOSYS+; seek/position operations on
console streams fail with +ESPIPE+. Floating-point +printf+ conversions and
+scanf+ scansets are not implemented. +fscanf+ can read the console stream but
not files. The standard does not require a file system for freestanding
implementations; this emulator's current data disks do not provide C streams.

+<locale.h>+ supports only the +"C"+ locale. +<time.h>+ provides calendar
conversion, formatting, and elapsed-time conversion in UTC. +localtime+ is
currently UTC as well. No real-time clock or processor-time counter is
available, so +time+ and +clock+ return their +-1+ failure sentinels. The
math interface contains software approximations only. All floating types map
to binary16, which does not meet C90's minimum +double+ range or precision;
math results, +HUGE_VAL+, and exceptional-value handling are not C90-accurate.
The project's screen and graphics routines are SC-16-specific extensions, not
replacements for standard facilities. Global initializers must be constant
expressions supported by the compiler.

+<math.h>+ is also available with the C90 function names and declarations.
The current software routines provide basic approximations for the listed
functions, but use the target's binary16 floating-point operations; they do
not provide C90's required +double+ range/precision or its full exceptional
value behavior. In particular, +HUGE_VAL+ is the largest finite target value,
not an IEEE infinity. Do not use this math subset for numerically sensitive
work or assume C90 numerical accuracy.

=== BIOS, Bug Monitor, and virtual disks

The guest-resident BIOS starts with a text-mode selection screen in the main
window. It uses bright green characters on black, with a fixed-width, enlarged
font and no glow or post-processing effects. It selects ID-named folder disks
from +disks/+; metadata is checked after selection. Exactly one regular
+kernel.bin+ or +main.bin+ is required. +kernel.bin+ authorizes KERNEL-mode
execution and must be trusted; this is not authenticated or secure boot.
+main.bin+ starts in USER mode. Both or neither produces +NOT_BOOT+.
The BIOS loads the selected SC-16 image directly, without compiling source.
Use Up/Down and Enter to select and boot.
The optional +--disk ID+ preselects a boot disk. With an explicit program
path, that option mounts the same folder filesystem for guest file operations.

Press Enter in the BIOS to boot the selected disk. The kernel installs its
IDT, enables the MMU and instruction timer, and starts the user-mode shell.
At the +sc16>+ prompt, enter +run demo+ to start the preemptive demo as a child
task. The shell reports the child's output and exit status, then returns to the
prompt. Other commands are +help+, +list+, +info+, and +ps+. The +ps+ command
lists all unreaped processes with their PID, parent PID, state, and program.
The shell itself is +running+ while it executes +ps+. +ready+ means eligible
to run but waiting for the CPU; +sleeping+ means blocked on a timer, +waiting+
means waiting for a child, and +blocked+ covers other waits. +exited+ processes
remain visible until reaped. This is a per-row state query, not CPU utilization.

Use +run demo X+ to launch a background demo for +X+ seconds (1 through 65535).
The shell returns immediately and accepts more commands, including additional
background launches. Each child prints +BGP [pid] time [second]/X+ once per
elapsed second, starting at +1/X+ and ending at +X/X+, then exits. For example:
[source,console]
----
sc16> run demo 3
Started background process 1
sc16> ps
PID PPID STATE PROGRAM
0 - running sisuos
1 0 sleeping demo.bin
running=on CPU, ready=waiting for CPU
sleeping=timer wait, waiting=child wait
BGP 1 time 1/3
BGP 1 time 2/3
BGP 1 time 3/3
----
Background output can appear while a command is being typed. Timing uses a
monotonic host clock and a blocking millisecond sleep service, not busy polling,
the instruction-tick sleep service, or emulation speed.
Overdue lines are emitted when execution next runs. Up to 16 background
children can be tracked at once; the shell reaps
finished children while reading input. The program list is fixed to +demo+ and
this example is not a general-purpose OS.

To build and install the SisuOS disk while preserving unrelated writable data:
[source,powershell]
----
.\programs\sisuos\tools\build.ps1 -Install
----
The kernel's protected-mode, interrupt, and MMU setup remains in
+programs/sisuos/src/preemptive_os_kernel.asm+. The interactive shell and preemptively
scheduled child program are written in C in
+programs/sisuos/src/preemptive_os_shell.c+ and +programs/sisuos/src/preemptive_os_demo.c+.
The build embeds the compiled shell in the kernel image and packages the
compiled child as +demo.bin+. A BIOS-boot integration test checks the packaged
images against those sources and verifies that the child task runs and exits.

The BIOS information block starts at +0x43040+: bytes +0..3+ are the +SC16+
signature, bytes +4..5+ are the BIOS version, bytes +6..8+ contain the memory
size, bytes +9..11+ contain the console data-register address, bytes +12..14+
contain the disk-control address, and byte +15+ is the startup status.
The status is +0+ after successful initialization or disk selection and +1+
when a disk cannot be mounted.

The serial device is memory-mapped at the legacy UART-like console addresses:

[cols="1,1,1"]
|===
|Address
|Register
|Meaning

|+0x43200+
|Data
|Write one output byte; read and remove one input byte.

|+0x43201+
|Status
|Bit 0: input available; bit 1: output ready; bit 2: input overflow. Write bit 2 as 1 to clear overflow.

|+0x43202+
|Control
|Bit 0 enables local echo; bit 1 enables host keyboard input. Both are enabled at reset.
|===

Guest console input and output use the main emulator display as an 80×25 text
terminal. Guest writes to standard output/error or +0x43200+ appear there;
keyboard input is echoed as the guest reads it. Carriage return, line feed,
backspace, tabs, wrapping, and scrolling are supported. The terminal also
supports ANSI CSI cursor movement, cursor positioning, line/screen erase, and
cursor save/restore sequences. A cursor marks the current insertion position.
The guest's existing graphics display remains available until it writes to
the console.

The optional *Bug Monitor* is separate from the guest terminal and displays
emulator diagnostics only. Its *CLOSE MONITOR* button and F2 hide the monitor
without changing guest execution. *COPY* copies selected text or the
visible monitor screen; Ctrl+C copies selected text. The 1,000-row diagnostic
scrollback can be navigated with the mouse wheel. Emulator lifecycle and
device errors are tagged by severity. Guest C programs can include
+<bug_monitor.h>+ and call the dedicated diagnostic logging functions:

[source,c]
----
bug_monitor_debug("entered update loop");
bug_monitor_info("player ready");
bug_monitor_warning("low on memory");
bug_monitor_error("unable to load level");
----

The functions write +[DEBUG]+, +[INFO]+, +[WARN]+, or +[ERROR]+ followed by
the message and a newline to the Bug Monitor; they do not appear in the guest
terminal. The guest console input path remains available to guest programs.
To start a new BIOS session, close and relaunch the emulator.
Type into the main emulator window to send input to the guest terminal; Enter
and Backspace are supported. Press F2 in the emulator window to hide/show the
Bug Monitor. An empty console-status poll yields the current instruction frame
to the host event loop, so a C +getchar+ wait does not prevent keyboard events
from being processed.

The guest filesystem is rooted at the folder disk selected by the BIOS or
+--disk ID+. The register service at +0x43100+ supports bounded listing, file
reads and replacement writes, directory creation, deletion, rename, and
metadata queries. Its command IDs and C register helpers are defined in
+toolchain/include/folder_fs.h+; +toolchain/include/disk.h+ provides file-reading and recursive-list
helpers for existing programs. Status at +\+16+ is +0+ on success and +1+ on
error. Paths are normalized, relative ASCII paths confined to the mounted
folder; transfers are limited to 4096 bytes. Filesystem operations cannot
access other disks or host paths.

The native C compiler also links an unbuffered hosted file-stream subset when
one of its supported file APIs is used: +fopen+, +freopen+, +fclose+,
+fgetc+, +fputc+, +fread+, +fwrite+, +fseek+, +ftell+, +ungetc+,
+clearerr+, +feof+, and +ferror+. These streams access the current folder
disk through the syscall ABI. +remove+ is explicitly unsupported and sets
+errno+ to +ENOSYS+; other standard stream, environment, and process facilities
remain incomplete. This is not a claim of complete hosted C90 support.

Images built and launched from a source path by +run.ps1+ without +--disk+
use that source program's +disks/+ directory through a host-configured
read-only mount. When a folder disk is selected, its data and policies take
precedence. Tank-16 reads maps and tile assets from its packaged folder disk.
The old JSON block format is no longer a guest device; original JSON files
remain available to +sc16build import-block-disk+.

Tank-16 uses this generic API to load map JSON from
+programs/tank-16/assets/disk/maps/+ at round start. The first round prefers
+FINLAND.json+; subsequent rounds randomly select among the JSON maps in that
folder. Finite maps use the map editor's tile-grid format. An infinite map
uses +"infinite": true+, a seed, row-major terrain tile IDs, and optional
obstacle density and tile IDs; terrain and obstacles are generated
deterministically from tile coordinates. Only graphics atlases are included in
the Tank-16 executable, not map data. The map editor mirrors saved maps into
the program's +disks/maps/+ folder.

Programs booted from a folder disk can access that selected disk through the
bounded USER-mode filesystem service in +#include "folder_fs.h"+. It supports
directory listing, file reads and replacement writes, directory creation,
entry deletion/rename, and metadata queries. Transfers are limited to 4096
bytes, paths are normalized disk-relative ASCII paths, and read-only disks,
protected paths, and boot executable names are enforced by the service. See
link:sc16_disk_format.adoc[+sc16_disk_format.adoc+] for the request registers
and result format. The older +disk.h+ file helpers remain for direct-source
developer launches and are not a substitute for the folder-disk service.

+<stdio.h>+ currently provides console +getchar+, +putchar+, +puts+, +gets+,
+fgetc+, +fgets+, +fputc+, +fputs+, +printf+, +fprintf+, +vprintf+, and +vfprintf+.
+gets+ follows C90 line-reading semantics and, like the standard function, does
not bound writes to the supplied buffer. The formatter
handles integer, character, string, and pointer conversions (+d+, +i+, +u+,
+o+, +x+, +X+, +c+, +s+, +p+, +n+, and +%%+) with field width and precision.
Unsupported conversions return +EOF+. File-backed streams and floating-point
conversions are still unimplemented; this is a useful hosted-I/O subset, not a
claim of complete C90 +stdio+ conformance.

Screen text input accepts printable ASCII and Latin-1 keys, echoes the entered
glyphs, and uses Enter as the line terminator. The library reserves scratch bytes near +0x4300+;
do not use that region for application data while a screen routine is running.
See link:../programs/text-demo/src/text_demo.c[+programs/text-demo/src/text_demo.c+] for a C example.

Generated C code uses the far control instructions (+JMPX+, +CALLX+, +BZX+,
+BCX+). Address 0 holds an entry stub; +0x0002+-+0x0005+ hold interrupt
vectors, and the boot routine at +0x0006+ calls +main+. Compiled code starts at
+0x4800+; global data starts at +0x80000+. Return addresses preserve the full
30-bit PC; code is no longer
restricted to addresses below +0x10000+ for call/return correctness. Libraries use fixed
low-memory locations: +lib_gfx+ at +0x400+, +lib_text+ at +0x700+, and
+lib_cgfx+ at +0x1000+. The compiler/assembler reports errors when emitted
sections overlap or stack frames exceed supported limits. The command-line
compiler writes a flat +.bin+ image with address gaps zero-filled; the emulator
loads it at address zero. In link:../examples/factorial.c[+examples/factorial.c+],
the global +result+ is stored at +0x80000+ after execution.

The preprocessor implements the directives and extensions listed above, but is
not certified against the full C90 translation limits or conformance suite.
For shifts, +>>+ is arithmetic for +int+ and logical for unsigned types.

=== C graphics library (+gfx_*+)

link:../toolchain/include/suomi_gfx.h[+toolchain/include/suomi_gfx.h+] declares the graphics builtins and defines color
(+RED+, +GREEN+, ...), key (+KEY_LEFT+, +KEY_FIRE+, ...) and screen-size
constants. Using any +gfx_*+ function makes the compiler link
link:../toolchain/runtime/lib_cgfx.asm[+toolchain/runtime/lib_cgfx.asm+], which drives the graphics coprocessor, plus the
font. Five hardware layers are composited from lowest to highest priority:
background/VRAM (0), tiles (1), sprites (2), 3D (3), and HUD (4) by default.
Higher priorities cover lower ones; equal priorities are ordered by layer
number. +gfx_layer_order()+ changes a layer's 8-bit priority. Zero is the
default transparent color for each layer. Layer visibility is selected with a
five-bit mask. +gfx_present()+ composites the enabled layers for display and
ends the current emulator frame; it does not copy or overwrite VRAM. The GPU
keeps layer, tile, and sprite storage outside the SC-16 CPU-visible address
space.

Everything is clipped to the screen. Held keys (bitmask at +0x43004+): bit 0
left/A, 1 right/D, 2 up/W, 3 down/S, 4 Space, 5 Enter, 6 Tab. The second byte
(+0x43005+, +gfx_keys_ext()+, constants +KEYX_*+) holds bit 0 Q, 1 E, 2 X/Shift, 3 Z/Ctrl.
The third byte (+0x43006+, +gfx_keys_ext2()+) uses +KEYX2_*+ constants; Tank-16
assigns bit 0 C, 1 J, 2 L, 3 I, 4 K, and 5 period. The mouse register block
starts at +0x43008+.

Speed register (+0x43003+): 0 = fixed speed (30 frames/s, 30000 instructions per frame), nonzero = maximum speed: the emulator drops the frame cap, skips most display refreshes and runs up to 300000 instructions per pass. User programs may write this register and the frame-synchronization register at +0x43013+; the adjacent interrupt-control register remains supervisor-only. Use it from C with +gfx_speed(1)+ / +gfx_speed(0)+; time maximum-speed runs with the real-time clock (+gfx_rtc+), since frame ticks no longer match wall time. Page 9 of the showcase uses it to measure the SC-16 for 3 seconds.

Mouse registers (base +0x43008+): +\+0+ X word, +\+2+ Y word, +\+4+ held buttons, +\+5+ events.
A double click is a second press of the same button within 400 ms and 4 pixels; it raises
the press bit and the double-click bit together. Drag and drop = button held while the
position changes; the release event marks the drop.

Coprocessor registers (base +0x43020+, 16-bit values big-endian and signed):
+\+0+ CMD (writing it runs the command), +\+1+ COLOR, +\+2+ X, +\+4+ Y, +\+6+ W,
+\+8+ H, +\+10+ SRC word, +\+12+ SRC high byte, +\+14+ RESULT. Commands: 1 clear,
2 pixel, 3 rect, 4 line (W,H are the end point), 5 sprite, 6 bitmap, 7 text
(NUL-terminated string at SRC), 8 present, 9 random (to RESULT), 10 polygon
(W is the point count), 13 sound (COLOR channel, X Hz, Y frames, W wave, H volume %),
14 save selected layer, 15 restore it, 16-20 networking (below), 21 upload tile map
(X/Y camera, W/H dimensions, SRC map), 22 3D scene, 23 sprite upload
(COLOR slot, W/H size, SRC pixels), 24 sprite move (COLOR slot, X/Y, W flags),
25 tile upload (COLOR tile ID, SRC 16x16 pixels), and 26 tile camera (X/Y).
Memory-mapped layer controls follow at +0x43030+: select layer, visible-layer
mask, five per-layer transparent-color registers at +0x43032+-+0x43036+, then
five composition-priority registers at +0x43037+-+0x4303B+ (one byte per layer).
Layer indices are background 0, tiles 1, sprites 2, 3D 3, HUD 4; bit N of the
mask enables layer N. Assembly programs can use these registers directly.

GPU command 22 draws a complete 3D scene from the 30-bit address in SRC. The
scene is an array of signed 16-bit words, in big-endian memory order:

[cols="1,1"]
|===
|Word offset
|Contents

|0-1
|Vertex count (3-128), triangle count (1-128)

|2-4
|Rotation around X, Y and Z; low byte is 0-255 units per full turn

|5-7
|X, Y and Z translation in signed 8.8 fixed-point

|8
|Positive focal length in 8.8 fixed-point

|9
|Flags: +GPU3D_FILL+ (1), +GPU3D_WIREFRAME+ (2), or both

|10 onward
|Vertices: X, Y, Z; each signed 8.8 fixed-point

|After vertices
|Triangles: three vertex indices and one palette color per face
|===

+GPU3D_FIXED(n)+ converts an integer coordinate to 8.8 format; +GPU3D_ONE+ is
. These signed 16-bit values range from -128 through 127.996. Scene buffers
may be byte-aligned at any address. The renderer performs integer X/Y/Z matrix
rotations, perspective projection, and flat
triangle filling. Faces are painted back-to-front by average vertex depth.
Wireframe edges are drawn with each face, so later faces cover hidden edges.
Triangles with a vertex at or behind the camera are skipped. +gfx3d_draw+
returns +GPU3D_OK+ (0) when accepted, +GPU3D_ERROR_SCENE+ (1) for an invalid
descriptor/count/flag/focal length, or +GPU3D_ERROR_FACE+ (2) for a face
referencing a nonexistent vertex. The renderer has no per-pixel depth buffer.
See the SC-16 showcase's 3D flight page for an example.

SC-NET is separate from the game networking API below. C programs that include
+toolchain/include/sc16_net.h+ can discover emulator node IDs, send messages to discovered
peers, and receive messages nonblockingly. Node IDs are set in BIOS and
collisions prevent disk boot. SC-NET uses a separate host UDP service on port
47017; it is transport infrastructure, while game programs continue to use
their own titles and application protocols.

=== LAN games (+net_*+)

Games can talk to other emulator instances on the local network without any server program:
every instance is a peer and finds the others with small UDP broadcast packets (port 47016,
change with +--net-port+; all players must use the same port). Instances only see peers that
called +net_open+ with the *same title* (up to 16 characters), so "pacman" ignores "elite".
At most 8 instances share a title; each gets a slot 0-7 (settled about 0.6 s after joining, +net_ready()+;
an already settled player keeps its slot against a newcomer). Peers that vanish time out after about 3.5 s; +net_close()+ leaves immediately.
Broadcasts are not delivered back to the sender. Delivery is UDP: messages can be lost or reordered,
so send state continuously rather than relying on single events.

|+void net_close(void)+
|Leave the group.

|+int net_send(unsigned char *data, int len)+
|Broadcast 1..+NET_MAX_MSG+ (48) bytes to all other instances; 1 = sent.

|+int net_recv(unsigned char *buf)+
|Pop the next message into +buf+; returns its length, 0 if none.

|+int net_sender(void)+
|Slot of the sender of the last received message.

|+int net_players(void)+
|Live instances including this one.

== 11. Reusable graphics library

link:../toolchain/runtime/lib_gfx.asm[+toolchain/runtime/lib_gfx.asm+] provides assembly-callable routines.
Include it after the main code (its routines occupy addresses starting at
+0x0400+):

[source,asm]
----
.address 0x0100
start:
    LDI R0, 20
    LDI R1, 20
    LDI R2, 25
    CALL GFX_PLOT
    HALT
.include "toolchain/runtime/lib_gfx.asm"
----

+CALL+/+RET+ and the full-width conditional branches support reusable routines.
The graphics library calling conventions are:

[cols="1,1,1"]
|===
|Routine
|Inputs
|Effect

|+GFX_PLOT+
|+R0=x+, +R1=y+, +R2=color+
|Write one palette index at a pixel. Preserves +R0+-+R3+; clobbers +R4+-+R7+.

|+GFX_CLEAR+
|none
|Clear all 320x240 pixels to color 0. Clobbers all registers.

|+GFX_HLINE+
|+R0=x+, +R1=y+, +R2=length+, +R3=color+
|Draw a horizontal line. Length must be 1-255. Clobbers +R0+, +R2+, and +R4+-+R7+.

|+GFX_RECT+
|+R0=x+, +R1=y+, +R2=width+, +R3=height+, +R4=color+
|Draw a filled rectangle. Width and height must be 1-255. Clobbers all registers.

|+GFX_SPRITE+
|+R0=x+, +R1=y+, +R2=width+, +R3=height+, +R4=data address+
|Draw row-major palette bytes; zero is transparent. Clobbers all registers.

|+GFX_TEXT+
|+R0=x+, +R1=y+, +R2=text-data address+, +R3=color+
|Draw 6x8 cells using the font include. Clobbers all registers.
|===

Coordinates are pixels from the top-left. Drawing beyond the screen is not
clipped. Pixel and sprite colors are palette indexes. A sprite is a sequence of
+width * height+ bytes; +.data hex+ is suitable for small sprites. Text data
consists of glyph IDs: printable ASCII uses its character code minus 31, IDs

These routines are simple reference implementations rather than optimized

execute many instructions per pixel. Use them sparingly in timing-sensitive
loops. Code, graphics scratch data, and the stack must not overlap.

== SC-16 showcase and timing/interrupt additions

GPU commands 11 and 12 (in addition to 1-10):

[cols="1,1,1"]
|===
|Cmd
|Name
|Effect

|11
|TICKS
|Frame counter written big-endian to RESULT (+14/+15)

|12
|RTC
|RTC register selected by COLOR (0 sec, 1 min, 2 hour) to RESULT (+14)
|===

C builtins include +gfx_ticks()+ and +gfx_rtc(field)+. Until a guest kernel
provides an interrupt/syscall service, +gfx_irq_init()+ is a no-op and
+gfx_irq_ticks()+ / +gfx_irq_keys()+ return zero; USER programs cannot install
interrupt handlers or execute +EI+. See
link:sc16_architecture.adoc[+sc16_architecture.adoc+] for the IDT and interrupt
frame contract. The C entry stub is +JMP __c_boot+ at 0 with boot code at 6.
C globals start at 0x80000.

Run the showcase (9 pages; Left/Right or A/D change page, Enter runs the benchmark on page 8 and a quick speed measurement on page 9, which compares the SC-16 in MIPS with the Intel 4004, 8088, 6502, 68000, 486DX2-66, CRAY-1 and Raspberry Pi A):

    cargo run --bin sc16build -- "programs/sc16-showcase/src/sc16_showcase.c" showcase.sc16img
    cargo run -- showcase.sc16img
