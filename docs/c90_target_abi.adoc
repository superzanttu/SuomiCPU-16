= SC-16 C90 Target ABI

This document records the target ABI decisions for completing hosted ANSI C90
support. Floating-point object representation, literal conversion, scalar
conversions, and generated arithmetic follow the rules below. The document is
not a claim that the compiler implements every C90 requirement; the compiler
remains nonconforming until the implementation and independent conformance
tests meet the acceptance criteria below.

== Data model

[cols="1,1"]
|===

|Target representation

|+char+, +signed char+, +unsigned char+
|8 bits; plain +char+ is signed

|+short+, +unsigned short+
|16 bits

|+int+, +unsigned int+
|16 bits

|+long+, +unsigned long+
|32 bits

|+float+
|IEEE-754 binary32, 4 bytes

|+double+
|IEEE-754 binary64, 8 bytes

|+long double+
|IEEE-754 binary64, 8 bytes

|object pointer
|30-bit byte address, stored in 4 bytes

|function pointer
|30-bit byte address, stored in 4 bytes
|===

Bytes are 8 bits. Multi-byte integer and floating representations are
big-endian. Integer signedness and ranges follow the representations above;
+long+ therefore provides the minimum range required by C90. +float+ and
+double+ are separate types in this target model. +long double+ has the same
representation and precision as +double+. The floating-point format decisions
meet the C90 minimum precision and range requirements.

=== Floating-point representations

The target uses the IEEE-754 binary interchange formats. +float+ is binary32:
one sign bit, an 8-bit exponent with bias 127, and a 23-bit trailing significand
field. +double+ and +long double+ are binary64: one sign bit, an 11-bit
exponent with bias 1023, and a 52-bit trailing significand field. Floating
objects use big-endian byte order. There is no additional alignment
requirement; the existing aggregate layout places objects larger than one
byte at even offsets.

Decimal floating constants without a suffix have type +double+; +f+/+F+
suffixes select +float+, and +l+/+L+ suffixes select +long double+. Conversion
to the destination format and every arithmetic operation round to nearest,
ties to even; consequently +FLT_ROUNDS+ is 1. Subnormals are supported
(gradual underflow), and signed zero is preserved. Overflow produces a signed
infinity; finite nonzero division by zero produces a signed infinity; invalid
arithmetic produces a quiet NaN.
Newly generated NaNs use the canonical positive encodings
+0x7FC00000+ for binary32 and +0x7FF8000000000000+ for binary64; NaN payload
propagation is not part of the ABI. NaNs do not trap: ordered comparisons with
a NaN are false, and NaN compares unequal to itself. Positive and negative
zero compare equal. Floating exceptions do not trap and no floating status
flags are exposed to C.

The ISA implements binary32 and binary64 add, subtract, multiply, divide,
ordered comparison, integer conversions, format conversion, negation, and
square root. A float value occupies an even pair of registers; a double or
long-double value occupies R0-R3 or R4-R7, most-significant word first.
Assembler mnemonics use the +F32+/+F64+ prefixes (+F32ADD+, +F64CMP+,
+I32TOF64+, +F64TOI32+, etc.) and reject register groups that cross these
boundaries. The Rust CPU implements these instructions directly. Float-to-integer conversion truncates toward
zero. The
instruction returns zero for non-finite input and the low destination bits for
finite values outside the destination range; C code must not rely on this
extension where C90 leaves the conversion result undefined.

The compiler converts decimal floating constants directly to the selected
binary format using round-to-nearest, ties-to-even. Unsuffixed constants have
type +double+, +f+/+F+ constants have type +float+, and +l+/+L+ constants have
type +long double+. In non-prototype calls, +float+ arguments are promoted to
+double+, as required by the default argument promotions. +float.h+ describes
the formats implemented here; its maximum, epsilon, and minimum constants
round to the corresponding binary32/binary64 values.

Pointer objects occupy four bytes. Their representation stores the low 16
address bits first, followed by the high 14 address bits; each 16-bit word is
big-endian. For example, address +0x01234567+ is stored as +45 67 01 23+.
This word order is specific to the pointer representation; other multi-byte
integer and floating representations are big-endian. Pointer arithmetic is
defined over the flat byte-addressed machine space but must still obey C90's
same-array object rules. The compiler must not silently truncate addresses or
offsets. Explicit pointer-to-integer conversions preserve the complete address
in a 32-bit +long+ and the low 16 bits in a 16-bit +int+. Explicit integer-to-
pointer conversions use the low 30 bits. These conversion choices are
implementation-defined.
Runtime tests verify reads through one-level pointer-to-const locals, globals,
and parameters, and reject assignments, compound assignments, and updates
through those pointers. Const-qualified scalar and bit-field record members,
standalone scalar objects, and arrays are initialized and reject later writes.
Qualifier-dropping conversions between simple pointer variables, fixed
pointer arguments, and pointer returns are also rejected. Multi-level
qualifier conversions and const-qualified pointer objects remain outside this
verified subset.

== Alignment and aggregates

The machine is byte-addressable and permits unaligned loads and stores, so this
ABI imposes no minimum address alignment on objects. Arrays have contiguous
row-major storage with no padding between elements.

For compatibility with the current layout, a non-union structure member whose
size exceeds one byte starts at the next even offset relative to the beginning
of the structure. Other members use the current offset. The size of every
structure or union is rounded up to an even number of bytes. Union members
start at offset zero. These are implementation-defined padding choices, not
hardware alignment requirements, and must be reflected identically by
+sizeof+, +offsetof+, initializer emission, address calculations, and runtime
accesses.

=== Bit-fields

The selected bit-field ABI uses 16-bit allocation units. Only +int+,
+signed int+, and +unsigned int+ bit-fields are supported; plain +int+ fields
are signed. A field's width must be between zero and 16. Fields are allocated
from the least-significant bit upward. Consecutive fields with the same
declared base type share an allocation unit while they fit; a field that does
not fit starts a new unit and never straddles two units. A nonzero-width
unnamed field reserves its bits. A zero-width field must be unnamed and starts
the next allocation unit. An allocation unit begins at an even structure
offset, consumes two bytes even when partially used, and uses the target's
big-endian word representation.

Each union bit-field member begins at bit zero of an allocation unit at offset
zero. Union size includes the largest member representation and is rounded up
to an even number of bytes. Bit-fields have no address, so applying +&+,
+sizeof+, or +offsetof+ to one is invalid. Signed fields use the low-width two's-complement
representation and sign-extend when read; unsigned fields zero-extend.
Assignments update only the selected bits in the allocation unit.

Execution tests verify signed and unsigned reads at every width from 1 to 16,
word-integer assignments and compound assignments, prefix/postfix updates,
integer promotions, and preservation of neighboring fields. Lvalue indices
are evaluated once, including assignment results and updates across calls.
Integer updates perform one allocation-unit read and one write, including
volatile fields; a discarded volatile field expression still reads its unit.
The tests inspect exact big-endian unit bytes, unnamed and zero-width fields,
unit boundaries, unions, nested members, global constant initializers, and
frame-local objects and arrays across recursion. Simple floating assignments
and automatic initializers convert to the declared integer type before field
narrowing. Invalid widths, base types, address-taking, and +sizeof+ uses are
diagnosed.

Scalar record layout uses the target four-byte +long+ and +float+ widths and
eight-byte +double+ width for global and frame-local objects. This size/layout
coverage accompanies tested runtime accesses to binary32/binary64 members and
indexed floating array fields, as well as signed/unsigned long scalar members
and indexed long arrays through nested and pointer-member expressions.
Automatic nested-brace initialization of records and multidimensional record
arrays executes side-effecting scalar expressions in declaration order and
zero-fills omitted fields and array elements.

This is a verified subset, not complete C90 bit-field support. Floating
compound assignments for addition, subtraction, multiplication, and division,
and wide-integer compound assignments are execution-tested. Direct writes and
updates to const-qualified scalar and bit-field members and standalone scalar and array
objects are rejected, while aggregate initialization of const members and
objects is tested. One-level pointer qualifier conversions remain a verified
subset; complete qualifier enforcement and the remaining general aggregate
initializer semantics still require the typed backend work.

== Function calls

Arguments are evaluated and pushed right-to-left. The stack grows toward
lower addresses. The caller removes arguments after return. The return address
occupies four bytes and stores the 30-bit PC in big-endian order. At function
entry, the first named parameter begins at +SP \+ 4+, followed by subsequent
parameters in declaration order; locals are
allocated below the entry stack position.

16-bit integer results use +R0+; 32-bit integer results use +R0:R1+, with the
high word in the even register. Pointer results use +R0+ for the low 16 address
bits and the low 14 bits of +R1+ for the high address bits. The machine
provides register-pair +CALLRP+ and +JMPRP+ operations for full 30-bit
addresses, but compiler parsing and calling through C function-pointer
declarators remain incomplete. 32-bit floating results use +R0:R1+ and
64-bit floating results use
+R0:R1:R2:R3+, from most- to least-significant word. Arguments use their
in-memory object representations on the stack, including the 4-byte pointer
representation.

Structure and union parameters are passed as copies of their complete object
representations; this caller-side copy convention is implemented for fixed
parameters. Structure and union assignment also copies complete object
representations. Structure and union returns use a caller-provided result
address as an implicit first argument; this pointer is removed with the
ordinary arguments by the caller. The compiler reserves per-call result
temporaries in the caller's stack frame, so recursive calls do not share
scratch storage. Runtime regressions cover nested return/argument expressions
and recursive returns.

=== Verified scalar call subset

The Rust compiler now shares scalar stack sizes and offsets between call
sites and function entries. Fixed byte parameters occupy one byte even in
mixed signatures; word parameters occupy two bytes, pointer and long
parameters four, binary32 parameters four, and binary64 parameters eight.
There is no inter-argument padding. Callees copy floating and wide-parameter
objects into their own frames, so parameter updates and recursive calls do
not share storage.

Execution tests in +tests/target_abi.rs+ verify exact incoming byte/word/
floating stack bytes, mixed pointer values, signed and unsigned long
arguments, nested binary32 calls, recursive binary64 calls, and caller stack
restoration. Large-arity tests cover 70 word parameters and 20 binary64
parameters, including cleanup exceeding one stack-adjustment instruction.
Precision conversions at fixed floating parameters and returns are checked
against independent IEEE bit patterns and Rust reference results. Integer
subexpressions retain integer evaluation before conversion at these boundaries.
Conflicting function parameter or return types are rejected before lowering.
Fixed-signature structure and union parameters are copied as complete object
representations. Execution tests cover mixed scalar offsets, nested records,
recursive aggregate calls, and isolation of the caller's objects.
Binary32 and binary64 scalar record members and indexed floating array fields
support tested loads, assignments, compound assignments, increments, nested
member access, and pointer-member access; global object bytes are checked
against the target representations.
Local pointers to binary32 and binary64 scalar objects support tested
dereference loads, stores, compound assignments, and prefix/postfix updates;
the regression keeps both pointers live together and checks the final global
object bytes.
Variadic calls apply the default promotions for tested signed/unsigned byte
arguments and binary32-to-binary64 arguments. An executing linked probe checks
the promoted bytes, pointer and aggregate representations, a following
wide-integer argument, fixed-parameter offsets, and caller stack restoration.
The compiler preserves the distinction between an empty parameter list (no
prototype) and a fixed +void+ prototype. Unprototyped calls use the tested
default promotions and stack representations; calls with extra arguments to a
fixed zero-parameter prototype are rejected. No-prototype declarations are
merged with compatible nonvariadic prototypes by checking parameter types
against the default-promoted types; incompatible mixtures are diagnosed.
K&R identifier-list definitions are not implemented.
Mixed binary32/binary64 arithmetic and narrowing/widening conversions are
checked against IEEE reference bytes, including unsigned conversion limits.
In-range floating-to-byte casts truncate toward zero before signed or unsigned
byte normalization; conversions between floating-point and pointer types are
diagnosed instead of being lowered as ordinary scalar casts.
Binary64 expressions and comparisons preserve live integer locals in R1-R3;
runtime tests exercise comparisons and truth conditions around those values.

=== Verified wide-integer scalar subset

Execution tests verify four-byte global and automatic +long+ / +unsigned long+
objects, scalar assignments and compound assignments, prefix/postfix updates,
arithmetic, bitwise operators, signed/unsigned division and remainder, shifts,
comparisons, conditions, short-circuit logic, and conditional expressions.
Wide expressions retain both words; narrowing conversions select the low
destination bits. Integer promotions distinguish signed 32-bit values from
unsigned 16-bit operands. Fixed long parameters and results use the documented
stack and register representations, including nested calls and recursion.

Runtime conversions between signed/unsigned 32-bit integers and binary32 /
binary64 are tested at initializers, assignments, casts, parameters, and
returns. Tests compare object bytes with independent Rust arithmetic and IEEE
references, including integer range edges and binary32 rounding at +16777217+.
Floating-to-integer cases stay within the destination's representable range;
the CPU's out-of-range conversion extensions are not C90 guarantees.
Locals whose writes produce expression values, and address-taken parameters,
use frame storage so evaluation and call register saves cannot undo writes.
Tests cover assignments and updates inside conversions and call arguments.
Binary32 and binary64 prefix/postfix increments and decrements execute for
local/global scalars and indexed array elements; tests verify pre-update and
post-update values and exact global object bytes.
Explicit scalar long/pointer casts retain all 30 address bits and discard
integer bits above bit 29. CPU address-value instructions retain the
architectural width even with a smaller configured RAM allocation; only
memory-access addresses are reduced to that allocation.

This scalar coverage does not establish complete wide-integer array, pointer,
aggregate-member, qualifier, or constant-expression semantics. Full typed
conversion analysis and general pointer/integer expression combinations remain
acceptance work.

These tests do not establish complete C90 call compatibility. Default argument
promotions, old-style function compatibility, complete typed expression
conversions, general wide-integer lvalues, aggregate call combinations,
and all pointer object encodings remain acceptance work. The historical
assembly-library calling paths are separate and retain their existing
conventions; their binary16 math routines are not binary64 C90 implementations.

== Hosted execution environment

The hosted implementation uses the emulator's byte-addressable 1 GiB
address space. Startup firmware exposes a descriptor at +0x43040+, an
interactive data-disk selector, and a memory-mapped console at +0x43200+.
Selected modules are still loaded into memory by the emulator; virtual disks
store program data only. The console currently supports a subset of standard
text streams and formatted output. File-backed streams, floating-point format
conversions, and several required C90 I/O facilities remain unimplemented.
Device-mapped addresses retain their documented SC-16 behavior. Compiler
global/static data is currently placed in +0x80000..0xFFFFF+; generated
addresses use +LDI30+ so this region and other addresses are not truncated to
16 bits. This allocation does
not reserve additional runtime heap or imply that every C90 translation-limit
requirement has been met. Screen and graphics APIs remain implementation
extensions and do not replace required C90 library interfaces.

== Conformance gates

The current code does not yet satisfy this target. In particular, C
function-pointer declarators and calls are incomplete, and the hosted library
is partial. Aggregate assignment, fixed-
parameter copies, and caller-owned record returns are implemented, but other
declarator and ABI requirements remain incomplete. Regression tests cover
30-bit pointer accesses and 30-bit return PCs, explicit
32-bit-integer-to-pointer casts, high-address byte/word/long accesses, and
indexed accesses crossing +0xFFFF+; these cases do not establish every pointer
conversion, arithmetic, alignment, or wraparound behavior.

Do not remove the compiler's nonconformance disclaimer until all of the
following pass:

. Compile-time and runtime ABI tests verify widths, ranges, endianness,
   alignment, aggregate offsets, pointer encoding, and all scalar/aggregate
   calling conventions.
. Rust CPU, compatibility emulator, and assembler execute identical tests for every C-visible
   memory, control-flow, and floating-point opcode. Calls and returns,
   including indirect calls, preserve all 30 PC bits; interrupt frames contain
   the four-byte PC and two-byte flags value.
. An independent C90 conformance suite passes, with each remaining failure
   categorized as a documented implementation-defined/unspecified behavior
   or fixed as a defect.
. Every required hosted C90 header and library interface is present and has
   behavior and boundary tests.
