= ANSI C90 Compatibility TODO

:experimental:
This roadmap divides the remaining C90 compiler work into two categories:

* *B — Basic C game programming:* compiler and runtime work that directly
  helps users write and run practical, ordinary C games on this platform.
* *C — Other C90 work:* remaining language completeness, hosted-standard
  library coverage, limits, independent conformance testing, and release
  certification.

These categories prioritize and explain the tasks; **both are needed for full
C90 compatibility**. Tasks may depend on items in another category.

*The compiler is not currently a fully conforming C90 implementation.* Keep
that disclaimer in link:user_guide.adoc[+user_guide.adoc+] until the release gates at
the end of this document pass. The ABI target is recorded in
link:c90_target_abi.adoc[+c90_target_abi.adoc+]; it contains intended
choices as well as existing behavior, so verify implementation before treating
an ABI choice as delivered.

SC-16 platform architecture, CPU features, target ABI prerequisites, boot,
disk, privilege, multitasking, virtual-memory, and syscall work are tracked in
link:sc16_improvements.adoc[+sc16_improvements.adoc+]. Architecture-dependent image
format, linking, and hosted file I/O must follow that plan's executable-image,
disk, and syscall contracts; do not create parallel designs here. This
document remains the checklist for C90 language, compiler, library, and
conformance work.

== Current baseline

* The compiler implements a substantial C90-oriented subset, but the user
  guide and ABI specification explicitly state that it is not yet conforming.
* Existing implementation and regression coverage include 32-bit +long+,
  30-bit object-pointer accesses, aggregate assignment and by-value argument
  copies, caller-owned structure/union returns, and supported one-level
  +const+ pointer-target qualification.
* The emulator provides 1 GiB of byte-addressable memory, and far control flow,
  return addresses, stack-pointer operations, and pointer accesses support
  30-bit addresses. Compiler global/static data occupies
  +0x80000..0xFFFFF+; +LDI30+ loads full addresses. Regression coverage
  exercises the C90 minimum 65,535-byte object size, but this does not establish
  all C90 translation limits.
* The assembler and Rust emulator provide binary32/binary64 floating-point
  instructions with interpreter fallback and focused opcode regressions. The C
  compiler now uses the target binary32/binary64 sizes for +sizeof+ and emits
  direct global floating initializers in big-endian form. Uninitialized
  automatic float objects and arrays reserve target-sized stack storage and
  have correct +sizeof+ values. Automatic float scalars and arrays, including
  multidimensional arrays, can be initialized from numeric literals; their
  object bytes can be inspected through character pointers. General initializer
  arithmetic constant expressions are supported for addition, subtraction,
  multiplication, division, and integer remainder. Automatic scalar +float+
  initializers also support runtime binary32 arithmetic (+-+, +*+, +/+,
  unary signs), loading local float values, and integer-to-float conversion,
  including integer arithmetic subexpressions in mixed expressions. Runtime
  binary32 comparisons (+==+, +!=+, +<+, +<=+, +>+, +>=+) are supported in
  automatic scalar initializers; tests cover unordered NaN behavior and
  conversion of a comparison result to +float+. General binary32 support now
  includes local/global/indexed-array/pointer-dereference loads and stores,
  scalar assignments and compound assignments, all six comparison operators in
  expressions and conditions, conditional and discarded expressions, and
  signed/unsigned 16-bit integer conversions in both directions. Calls with a
  single binary32 parameter and binary32 result are supported. Binary64 runtime
  coverage now includes tested scalar/pointer-array and scalar-pointer
  dereference access, arithmetic,
  comparisons, signed 16-bit conversion, and a single-parameter call/result.
  Fixed multi-argument, nested, and recursive floating calls are tested.
  Scalar signed/unsigned 32-bit expressions and conversions to/from both
  floating widths now execute at assignments and fixed call boundaries,
  including wide results, recursion, range edges, and binary32 rounding.
  Full typed lvalue and C90 usual arithmetic conversions remain incomplete.
  Constant casts to +float+, +double+, and +long double+ are supported in
  these initializers.
  Tests verify +float.h+ limit macros,
  binary32/binary64 maximum, minimum-normal, epsilon, subnormal, and
  halfway-rounding object encodings, including rounding a +float+ constant
  before promotion to +double+. Existing math routines still use binary16
  arithmetic; this partial compiler support does not establish C90 floating
  range or precision at runtime.
* Function pointers and indirect calls, bit-fields, full linkage/storage
  semantics, complete hosted standard-library facilities, and independent
  conformance validation remain incomplete.
* Repository regression tests do not substitute for an independent C90
  conformance suite. +tests/c90_conformance.rs+ sends compiler-emitted assembly
  through the assembler and executes the resulting image on the CPU for
  supported integer expressions and control flow, calls, arrays/pointers,
  preprocessing, and standalone header smoke tests. It also checks that the
  normal compile-to-image API matches an independently assembled image and
  locks in rejection of selected unsupported features and the current
  +setjmp.h+/+signal.h+ gaps. Header smoke tests do not establish library
  function conformance or complete C90 compatibility.

does not establish language feature parity.

The repository uses Rust for runtime, build, tools, and CI. Some legacy
integration coverage has not yet been recreated as Rust tests. C programs
outside the current native subset fail with an unsupported-program diagnostic.
Text Demo and the other pre-migration application sources are not evidence of
complete C90 support. The shared program command discovers all package
manifests, but unsupported C syntax and removed guest headers remain build
limitations.

== B — Basic C game programming

These tasks prioritize practical programs such as small games: ordinary
functions and declarations, numeric calculations, mutable game state,
initialization, and useful runtime facilities. They do not replace the full
C90 requirements listed under C.

=== B1. Implement C90 floating-point compiler support

* [ ] *Implement floating-point code generation* (+c90-float-backend+)
** Step 1: Add typed floating-expression analysis for literals, lvalues,
   casts, integer signedness, and C90 usual arithmetic conversions. Reject
   unsupported conversions explicitly.
** Step 2: Implement general binary32 and binary64 lvalue reads and writes for
   local, global, and indexed objects; cover assignments and compound
   assignments.
** Step 3: Implement signed and unsigned 16-bit / 32-bit integer conversions
   to and from both floating widths, binary32/binary64 conversions in both
   directions, and conversion boundary diagnostics/tests.
** Step 4: Extend binary32 arithmetic and all six comparisons from automatic
   initializer expressions to general expression contexts, conditions,
   conditional expressions, and discarded expressions.
** Step 5: Implement binary64 arithmetic and comparisons and mixed-precision
   expressions using C90's usual arithmetic conversions.
** Step 6: Implement floating-point function arguments, return values,
   prototype conversions, and default argument promotions according to
   +c90_target_abi.adoc+, including nested and recursive calls.
** Step 7: Add end-to-end execution tests for operations, conversions, memory
   representation, comparisons, calls, and returns; compare results against an
   independent reference and document verified target behavior.
** Verified progress: fixed-signature scalar calls now use shared stack
   layouts, including multiple and mixed binary32/binary64 parameters, nested
   calls, recursion, and tested prototype/return precision conversions.
   Runtime tests inspect argument bytes, stack cleanup, and independent IEEE
   results. Full typed conversions remain open.
** Verified progress: binary32 and binary64 scalar truth conversions treat
   NaNs as true and positive or negative zero as false in conditions, logical
   expressions, and conditional expressions.
** Verified progress: executing C90 regressions cover signed and unsigned
   16-bit and 32-bit floating-to-integer conversions within the destination
   range, truncation toward zero, signed and unsigned 32-bit integer conversion
   edges to binary32/binary64, and IEEE unordered comparisons for both floating
   widths. The floating-point backend and full conversion analysis remain open.
** Verified progress: binary64 expression and comparison code preserves full
   30-bit register values across nested evaluation. An executing C90 regression
   verifies binary64 object bytes after runtime float-to-double conversion and
   comparison, covering the stack-pointer truncation caused by 16-bit saves.
** Verified progress: end-to-end execution checks all six ordered comparison
   operators for binary32 and binary64, mixed-precision operands, and
   comparison-driven conditional expressions; unordered NaN cases are tested
   separately.
** Verified progress: +long double+ runtime arithmetic, parameter/return
   passing, and exact binary64 object bytes execute through the documented ABI.
** Verified progress: supported variadic prototypes apply integer promotions
   to tested signed/unsigned byte arguments and promote binary32 arguments to
   binary64. An executing linked probe verifies stack offsets, promoted bytes,
   pointer and aggregate arguments, wide-integer representation, and caller
   cleanup. The parser distinguishes empty parameter lists from +void+
   prototypes; unprototyped calls apply the same tested promotions. Compatible
   prototype/no-prototype declarations are merged, while types changed by
   default promotions are rejected. K&R identifier-list definitions and full
   cross-translation-unit compatibility remain open.
** Verified progress: signed/unsigned long scalars now retain both words in
   arithmetic, comparisons, conditions, updates, fixed arguments, and results.
   Runtime conversions to/from binary32 and binary64 cover in-range edges,
   truncation, and rounding against independent Rust/IEEE references.
   Frame-backed expression writes prevent conversion/call register saves from
   restoring stale local or parameter values. Nested and pointer-member long
   fields and indexed long arrays support tested loads, stores, updates, and
   bytes. General pointer/dereference lvalues, pointer conversions, qualifiers,
   and constant-expression semantics remain open.
** Verified progress: binary32 and binary64 prefix/postfix updates execute for
   local/global scalars and indexed array elements, with runtime checks for
   returned old values, stored values, and exact global bytes. Scalar floating
   record members and indexed floating array fields support nested and pointer
   access and updates; scalar member initialization and global object bytes are
   tested. Typed conversion analysis and broader floating-lvalue coverage
   remain open.
** Verified progress: binary64 expressions now narrow to binary32 for scalar,
   indexed, record-member, and pointer-dereference assignments and compound
   assignments. All four compound operators execute across those lvalue forms;
   regressions also verify halfway rounding and preservation of the local
   frame pointer after mixed-precision compound operations. Conditional
   binary64 expressions convert at binary32 assignment, indexed lvalue
   side-effects are evaluated once, and unsigned 32-bit integer operands
   convert correctly in binary32 compound assignments. Invalid mixed
   floating-point/pointer arithmetic, comparisons, conditional operands, and
   assignments now produce compiler diagnostics rather than scalar lowering.
   These diagnostics also classify pointer-returning calls, floating-pointer
   return types, and string literals as pointer operands. Pointer-returning
   integer calls retain their element signedness and width when dereferenced.
   Taking the address of a global binary32/binary64 scalar is supported,
   including returning and dereferencing that pointer.
   Floating operands to remainder, shifts, bitwise operators, and bitwise
   compound assignments are likewise rejected with integer-operand
   diagnostics. Binary32 function results are accepted as compound operands
   for binary32 and binary64 lvalues.
** *Depends on:* +c90-float-model+ and +c90-float-isa+ in
    link:sc16_improvements.adoc[+sc16_improvements.adoc+].

== C — Other C90 compatibility work

These tasks close the remaining language and hosted-environment requirements
that go beyond the practical game-programming milestone. They are still
required before claiming full C90 compatibility.

=== C1. Complete pointer qualifiers

* [ ] *Complete C90 pointer qualifier semantics* (+c90-pointer-qualifiers+)
** Track +const+ and +volatile+ at every pointer level through declarations,
    typedefs, casts, conditional/comma expressions, members, prototypes,
    arguments, and returns.
** Distinguish a const-qualified pointer object from a pointer to const data.
** Reject qualifier loss and writes through const-qualified lvalues.
** Add positive/negative tests for multi-level pointers and all expression
    and declaration paths.
** Verified progress: one-level pointer-to-const reads through local, global,
    and parameter pointers execute; stores, compound assignments, and
    increments/decrements through those pointers are rejected. Writes and
    updates to const-qualified scalar and bit-field record members are rejected
    while aggregate initialization remains supported. Direct assignments and
    updates to supported const scalar and array objects, including const
    parameters and globals, are rejected. Qualifiers on pointer objects are
    diagnosed as unsupported. Qualifier-dropping conversions between simple
    pointer variables, fixed pointer arguments, and pointer returns are
    rejected. Addressing const objects and arrays cannot be assigned to
    unqualified pointers, passed to unqualified pointer parameters, or returned
    through unqualified pointer results. Provenance through conditional and
    comma expressions, pointer casts, and direct function-call results is also
    checked for qualifier loss and writes. Other expression paths and
    multi-level qualification remain incomplete.
** *Depends on:* B2a (+c90-function-pointer-types+).

=== C3. Complete preprocessing semantics

* [ ] *Complete C90 preprocessing semantics* (+c90-preprocessor+)
** Verified progress: active +#error+ directives now fail preprocessing with
   macro-expanded diagnostic text, inactive +#error+ directives are ignored,
   and +#pragma+ directives are ignored because this implementation defines
   no pragmas. Null directives and directives following comments are
   recognized. +#line+ updates token locations and macro snapshots, including
   macro-expanded line numbers and filenames; +__LINE__+ and +__FILE__+ expand
   at their use locations. Function-macro argument prescan, stringification
   whitespace, token pasting, and rescanning have focused tests. Other
   predefined macro requirements and remaining translation phases are still
   incomplete. C90 trigraphs are translated before line splicing, directives,
   and tokenization.
** Audit preprocessing translation phases and directives against C90.
** Implement macro argument prescan, stringification, token pasting,
    rescanning, and +defined+ behavior.
** Verify conditional-expression integer evaluation, include behavior,
    diagnostics, line mapping, and trigraph/splice ordering.
** Add tests independent of code generation.

=== C5. Implement all required C90 headers

* [ ] *Implement all required C90 headers* (+c90-required-headers+)
** Partial implementation now includes the console-only +<stdio.h>+ interface
    and a +printf+ integer/text formatter; C90 +gets+ is present, but floating
    conversions and file-backed streams remain outstanding. +<setjmp.h>+ now
    provides +jmp_buf+, +setjmp+, and +longjmp+; tests cover restored control
    flow, zero-value conversion, and unwinding a nested call. +<signal.h>+
    remains missing because signal-handler dispatch depends on function-pointer
    support. The exposed +stdio.h+ limits now meet the C90 minimum values for
    +BUFSIZ+, +FOPEN_MAX+, and +TMP_MAX+; this does not imply file-backed stream
    support, which remains outstanding.
** +<math.h>+ now declares the C90 math interface and links software
    approximations. These use the target's binary16 arithmetic and do not meet
    C90 +double+ range, precision, or exceptional-value requirements.
** The emulator now supplies a text console, BIOS device descriptor and
    required shared +firmware/bios.bin+ startup, folder-disk boot selection, and a
    bounded USER-mode folder-filesystem register service. System-call ABI
    version 1 and SC-16-specific C wrappers are now defined in
    link:sc16_improvements.adoc[+sc16_improvements.adoc+] and

** Add missing required declarations, macros, and types.
** Verify standalone use, repeated inclusion where permitted, and varied

== Completion criteria

Do not describe the compiler as fully C90-compatible until all of these are
true:

. Required language constraints, declarators, conversions, initialization,
   preprocessing, and translation limits are implemented and tested.
. The data model meets C90 minimum ranges and precision; scalar, pointer,
   aggregate, and function-call ABI behavior is verified.
. Required hosted headers and library facilities have documented and tested
   behavior, including errors and unavailable resources.
. Assembler and both emulator implementations agree on generated programs and C-visible
   machine behavior.
. An independent C90 conformance suite has been run; failures are resolved
   or correctly classified, and implementation-defined/unspecified behavior
   is documented.
. The user guide, ABI document, and this checklist accurately describe the
   implementation and the evidence supporting any conformance claim.
