= SC-16 Machine Architecture
:toc: left
:toclevels: 2

== Status and scope

This document defines the target machine contract and records the relevant
legacy behavior during migration. Target rules are normative for new CPU,
firmware, and kernel work; they do not imply that the emulator already enforces
them. The guest character-cell display and guest-resident BIOS are implemented.
The host renders an error screen only when the firmware image cannot be loaded.

== Machine model

SC-16 is byte-addressed with 30-bit addresses, for an address space of
0x00000000 through 0x3fffffff. Multi-byte values are big-endian. Instructions
are based on 16-bit words; prefixed instructions consume their encoded
extension words. The ISA opcode and encoding tables are maintained in
`src/emulator/isa.rs` and the assembler. General registers are R0 through R7; the
architectural flags are zero, carry, negative, and overflow. The control-flow
ABI stores return addresses as four bytes and preserves all 30 address bits.

The physical address space is 1 GiB. The top 1 MiB,
`0x3ff00000..0x3fffffff`, is reserved for device banks, never ordinary RAM.
Usable physical RAM is `min(configured backing size, 0x3ff00000)` bytes,
so the default 1 GiB backing provides 1023 MiB of usable RAM. The canonical
boundary is defined in `src/emulator/machine.rs`. Images, frame allocation,
page-table/IDT storage, and initial stacks exclude this aperture even when
host backing exists there. Smaller emulator memories remain
available for tests and must reject accesses outside configured memory rather
than silently wrapping. Multi-byte memory values are big-endian; unaligned
accesses are permitted when every byte is valid and permitted. Address
translation and permission checks apply independently to every byte of an
access.

The system identification, interrupt/PIT, fault, input, clock/random, graphics,
audio, game-network, filesystem, console, firmware-text and firmware-gateway
banks are implemented in this aperture without RAM backing. All other high
banks remain reserved. The low console/text, interrupt/PIT, RTC, fault and BIOS
aliases have been retired and their addresses are ordinary RAM. Legacy low
graphics and disk register windows remain reserved and supervisor-only until
those interfaces are removed. Instruction operands retain architectural
address bits before high-device checks, including on small-memory machines;
device accesses cannot be masked into low RAM. Legacy wrapping of nondevice RAM
accesses remains during migration.

=== High device map and register contracts

The canonical bank addresses are defined in `src/emulator/machine.rs`.
`toolchain/include/sc16_machine.h` exposes the same addresses for privileged C;
a test checks every definition against the Rust contract. These constants do
not grant user code access to devices. Privileged assembly can use the numeric
addresses below; no shared assembly constant syntax is currently supported.

[cols="1,1,2"]
|===
|Base |Bank |Implementation
|`0x3ff00000` |System identification |Implemented, read-only
|`0x3ff01000` |Interrupt/PIT |Implemented
|`0x3ff02000` |Fault status |Implemented, read-only
|`0x3ff03000` |Input |Implemented, read-only
|`0x3ff04000` |Clock/random |Implemented
|`0x3ff05000` |Graphics |Implemented
|`0x3ff06000` |Audio |Implemented
|`0x3ff07000` |Game network |Implemented
|`0x3ff08000` |Filesystem |Implemented
|`0x3ff09000` |Console |Implemented
|`0x3ff0a000` |Firmware text |Implemented
|`0x3ff0b000` |Firmware gateway |Implemented
|===

Each bank occupies a 4096-byte page. All remaining aperture pages are reserved.
System registers are unsigned 32-bit big-endian values, readable bytewise and
unaligned. They have no read side effects, writable bits, commands or overflow
behavior. They are immutable after CPU creation; image-entry preparation does
not change them.

[cols="1,1,3"]
|===
|System offset |Register |Value
|`0x00` |Machine revision |`2`
|`0x04` |Device ABI |`1`, identifying this bank contract
|`0x08` |Usable RAM bytes |Configured backing size capped at `0x3ff00000`
|`0x0c` |Address bits |`30`
|`0x10` |Implemented high banks |Bit N denotes bank page N; currently `0xfff`
|===

Revision 2 identifies the high-address device contract. SC16IMG3 images encode
this revision; older and unversioned images are rejected by runtime loaders.

Every high device access is supervisor-only and nonexecutable, regardless
of user/executable bits in a forged page-table entry. MMU translation permits
supervisor data access to implemented pages independently of RAM
size, but the CPU additionally checks each register byte. Undefined offsets
and unimplemented banks fault with `PhysicalOutOfRange`. Reads/writes by
user code to implemented pages fault with `SupervisorOnly`; supervisor fetches
fault with `NotExecutable`, and writes to read-only registers fault with
`ReadOnly`. Multi-byte accesses are fully checked before any read or write;
aliases report the original virtual fault address.

Page-table helpers permit borrowed device mappings only with supervisor,
nonexecutable permissions. Device mappings never allocate, reserve, clear,
free or count device frames as RAM. Page tables themselves must remain in RAM.
Validated transfer buffers and exception frames remain RAM-only, including
through supervisor device aliases. The host's infallible physical read/write
helpers assert on invalid high device accesses; guest access errors are
validated and delivered as CPU faults rather than host assertions.

==== Interrupt/PIT bank

[cols="1,1,1,3"]
|===
|Offset |Bytes |Access |Meaning
|`0x00` |1 |RW |Global interrupt enable, bit 0
|`0x04` |1 |R |Pending sources: keyboard bit 1, RTC bit 3, PIT bit 4
|`0x05` |1 |RW |Write-one-to-clear pending sources; reads return zero
|`0x06` |1 |RW |PIT delivery enable, bit 0
|`0x08` |2 |RW |Big-endian PIT period in CPU timer advances; zero disables counting
|`0x0c` |2 |R |Big-endian remaining PIT countdown
|===

All other offsets are reserved. Reserved value bits are ignored on writes and
read as zero. Reads have no side effects. Creation sets global enable, pending,
period, countdown and the period staging latch to zero; PIT delivery starts
enabled. Image-entry preparation clears global enable and all pending sources,
retaining PIT configuration and countdown, matching the existing boot path.

Writing the period high byte only stages it. Writing the low byte commits the
staged high byte plus the new low byte and reloads the countdown. Period reads
return the committed value, not staging. A fully validated word store therefore
commits once; a rejected store changes neither staging nor timer state.
Writing zero disables counting without clearing a previously pending tick.
There is no arithmetic overflow: the countdown reloads its unsigned 16-bit
period at expiry and latches one pending bit. Multiple expirations coalesce.

PIT delivery masking does not stop counting or clear pending ticks. Enabling
delivery exposes the latched tick at the next interrupt check when global
interrupts are enabled. Priority remains keyboard, PIT, RTC. Delivery clears
that source's pending bit; interrupt-gate entry clears global enable, and RTI
restores the saved enable state. The same controller supports guest-owned
IDT/PIT scheduling without emulator-managed tasks. The timer advances after
executed instructions and during existing host-managed idle scheduling; it is
not a wall-clock frequency guarantee.

Interrupt control, PIT configuration and pending state are exposed only through
the high interrupt bank. The former low ICR, PIT mask and period addresses are
ordinary RAM and do not update controller state. High register writes never
index or wrap into RAM.

==== Fault bank

[cols="1,1,1,3"]
|===
|Offset |Bytes |Access |Meaning
|`0x00` |4 |R |Big-endian original virtual address of the last recorded page fault
|`0x04` |2 |R |Big-endian fault information: access in high byte, reason in low byte
|`0x06` |1 |R |One if a page fault has been recorded, otherwise zero
|===

All other offsets are reserved. Access values are fetch 0, read 1, write 2.
Reasons are address-out-of-range 1, not-present 2, read-only 3, supervisor-only 4,
not-executable 5, malformed-entry 6 and physical-out-of-range 7.
Fault state starts at zero and is cleared by image-entry preparation. Recording
a fault replaces all fields before dispatching its handler, independently of RAM
size. Reads neither acknowledge nor clear it; all writes fault as read-only.
There is no command or overflow behavior. Translated device aliases retain the
original virtual address, not the physical bank address. The former low fault
register addresses are ordinary RAM and do not mirror fault state.

==== Input bank

[cols="1,1,1,3"]
|===
|Offset |Bytes |Access |Meaning
|`0x00` |1 |R |Last keyboard event byte; reading consumes it
|`0x04` |4 |R |Big-endian held-key mask; only bits 0..23 are defined
|`0x08` |2 |R |Big-endian unsigned mouse X
|`0x0a` |2 |R |Big-endian unsigned mouse Y
|`0x0c` |1 |R |Held mouse buttons: left bit 0, right bit 1
|`0x0d` |1 |R |Latched mouse events; reading clears all event bits
|`0x0e` |2 |R |Big-endian signed 16-bit per-frame wheel delta
|===

All other offsets are reserved. All writes fault as read-only. Devices start
with zero key, held mask, coordinates, buttons, events and wheel; there are no
commands or writable value bits. The keyboard event retains the latest byte
until read; a later event replaces an unread byte. Zero means no event. This
preserves the existing single-event hardware latch, not a keyboard FIFO.
Signalling a keyboard event also latches the keyboard interrupt. Reading its
byte does not clear the interrupt pending bit, and interrupt delivery does not
consume the byte.

Mouse event bits 0/1 mean left/right press, 2/3 double-click, and 4/5 release.
Events coalesce until read. A second press within 400 milliseconds and four
pixels on each axis counts as a double-click; that pair is then consumed by
double-click detection. Held state is independent of event consumption.
Position is clamped to 320x240 or 640x480 according to the active video mode.
Wheel updates accumulate with signed 16-bit saturation until the existing host
end-of-mouse-frame hook clears them. Reading wheel does not clear it.

Keyboard and mouse-event reads through high or translated device addresses
consume the same typed latch exactly once. Every byte of a multibyte access is
validated before consumption, so an access crossing reserved bytes or failing
permissions leaves events intact. Other input reads have no device side effects.
Input state and double-click history survive image-entry preparation; interrupt
pending state is separately cleared by that path.

The high bank exposes held keys as a conventional big-endian 32-bit value with
a zero high byte. Host input producers and valid destructive reads update only
the typed device state; direct host RAM mutation is not an input API. High input access works even when no legacy backing exists.

==== Graphics bank

The supervisor-only graphics bank offers bounded framebuffer commands through
typed registers. It never aliases high registers into legacy RAM, accepts no
guest pointers, and exposes no direct framebuffer memory. Coordinates are
unsigned pixel coordinates in the active 320x240 or 640x480 mode. Every draw
operation validates the complete region before modifying any pixels.

[cols="1,1,1,3"]
|===
|Offset |Bytes |Access |Meaning
|`0x00` |1 |W/R0 |Commit staged operation with value 1; reads return zero
|`0x01` |1 |R |Status: 0 success, 1 invalid commit value, 2 invalid operation or arguments
|`0x02` |1 |RW |Operation: 1 clear, 2 pixel, 3 rectangle, 4 line, 5 present, 6 inline blit, 7 palette, 8 mode
|`0x03` |1 |RW |Color index; palette operation uses this as the palette index
|`0x04` |2 |RW |X coordinate, unsigned big-endian
|`0x06` |2 |RW |Y coordinate, unsigned big-endian
|`0x08` |2 |RW |Rectangle/blit width or line endpoint X, unsigned big-endian
|`0x0a` |2 |RW |Rectangle/blit height or line endpoint Y, unsigned big-endian
|`0x0c` |2 |RW |Inline data length, unsigned big-endian, maximum 512
|`0x0e` |2 |R |Result: drawn pixel count, saturated at 65535; present returns frame count
|`0x10` |512 |RW |Inline blit pixel bytes or three RGB palette bytes
|`0x210` |1 |RW |Display mode: 0 is 320x240, 1 is 640x480
|===

All multibyte registers are big-endian. All other offsets are reserved.
Clear fills the active base layer and returns zero. Pixel returns 1;
rectangle and line return the number of drawn pixels; present sets the normal
frame-yield/present flags and returns the current frame counter. Rectangle
coordinates and dimensions must describe a nonempty region entirely inside the
active mode. Line uses X/Y as the start and width/height as the endpoint; both
endpoints must be inside the mode. Blit requires nonzero dimensions, an exact
`width * height` byte length no greater than 512, and a fully in-bounds region.
Palette requires data length 3 and sets the selected entry to RGB. Mode accepts
only 0 or 1 and clears the auxiliary layers when the mode changes. Other
operations require zero data length. Malformed commands leave framebuffer and
palette state unchanged; failures clear result and set status. Staging and
status persist across image entry, and no operation reads guest RAM.

==== Audio bank

[cols="1,1,1,3"]
|===
|Offset |Bytes |Access |Meaning
|`0x00` |1 |RW |Command: 1 submit staged sound, 2 stop staged channel; reads return zero
|`0x01` |1 |R |Last command status: 0 accepted, 1 invalid command, 2 invalid channel, 3 invalid waveform, 4 invalid volume
|`0x02` |1 |RW |Staged channel, valid values 0..3 at command commit
|`0x04` |2 |RW |Staged unsigned frequency in Hz
|`0x06` |2 |RW |Staged unsigned duration in 1/60-second frames; zero loops
|`0x08` |2 |RW |Staged waveform: 0 square, 1 noise, 2 triangle
|`0x0a` |2 |RW |Staged unsigned volume 0..100; zero retains legacy full-volume meaning
|`0x0c` |1 |R |Pending-command mask, bit N for channel N
|===

All multibyte registers are big-endian and all other offsets are reserved.
Creation sets staging, status and pending mask to zero. Staging writes retain
all bits and do not enqueue sound; a command byte commits an immutable copy.
Submit validates command, channel, waveform and volume in that order. Every
invalid operation records its explicit status without replacing any pending
sound. Stop validates the channel but ignores frequency/duration/waveform/volume,
enqueuing a zero-frequency command with the remaining parameters zero. Successful
commands clear a previous error status. Commands do not clear or rewrite staging.

The four pending slots are shared with legacy GPU sound commands. The last
accepted command for each channel replaces any unconsumed command for that
channel; other channels remain independent. Host consumption takes each slot
exactly once in channel order. Pending means awaiting host consumption, not
currently playing or successful host audio output. Reads of command, status,
staging and pending have no side effects; no register polls yield or block.
Rejected multi-byte accesses cause CPU faults before changing staging, status
or pending sound. There are no writable reserved bits or asynchronous device
commands. Audio staging/status/pending state survives image-entry preparation,
matching the existing sound-queue lifetime.

Both interfaces deliver the same typed sound commands to the existing host
renderer. Frequency zero stops that channel; other frequencies are clamped to
20..11025 Hz at rendering. Duration uses unsigned 16-bit frames, with zero
looping until replacement/stop; volume zero means 100%, not silence. Runtime
audio-device failures remain host runtime errors, not an accepted-sound guarantee.
The high bank rejects unsupported waveforms/volumes explicitly; the migration
alias retains legacy channel masking, waveform fallback and volume clamping.
Legacy GPU parameter bytes do not modify high audio staging or status. No audio
command accepts a RAM pointer, and high audio accesses never index RAM.

==== Game-network bank

[cols="1,1,1,3"]
|===
|Offset |Bytes |Access |Meaning
|`0x00` |1 |RW |Command: 1 open, 2 close, 3 send, 4 receive, 5 query; reads return zero
|`0x01` |1 |R |Last command status
|`0x02` |1 |RW |Staged transmit length, 0..48 at send commit
|`0x03` |1 |RW |Staged query selector, 0..6 at query commit
|`0x04` |2 |RW |Staged unsigned query argument
|`0x06` |2 |R |Last command result
|`0x10` |16 |RW |Staged game title
|`0x20` |48 |RW |Staged transmit payload
|`0x50` |48 |R |Last successfully received payload, zero-padded
|===

Multibyte registers are big-endian; all other offsets are reserved. Creation
zeros all registers and buffers. Staging retains every written bit and has no
network effects. Only a command byte commits an operation; commands do not
change staging. Registers, receive payload and the shared network node survive
image-entry preparation. No high-bank operation accepts a guest RAM pointer.

Status is 0 for success, 1 for invalid command, 2 for transmit length above 48,
3 for an empty title, 4 for send/receive without an active local slot/open node,
5 for a host socket/open/send failure, 6 for no queued receive packet, or 7 for
an invalid query. Host failures are also logged to the debug console. Every
command resets result to zero; validation errors do not poll, change the node,
or consume messages. Only parameters relevant to that command are validated.
Open uses bytes before the first NUL, or all 16 bytes if no NUL exists; the first
byte must be nonzero. Empty-title rejection leaves an existing connection intact.
A valid open retains the existing transport's close-then-open behavior.

Open returns 1 once the local UDP socket/title is established. Send returns 1
only after the OS accepts the datagram; UDP delivery is not guaranteed. Socket
errors return status 5 rather than a successful-send result. Zero-length
datagrams are permitted. Close is idempotent and returns zero. Receive consumes
at most one packet from the shared bounded inbox, returns its length 0..48,
and replaces/zero-pads the receive window. Status distinguishes a successful
empty datagram from an empty inbox. Failed/empty receives retain the prior
payload but return result zero. Reads never poll, consume packets or yield.
Rejected multibyte accesses fault before any command or staging side effect.

Query explicitly polls and snapshots one value into result: 0 player count,
1 local slot (`0xffff` if absent), 2 whether the argument slot is active,
3 game-full flag, 4 last consumed sender, 5 join-ready flag, or 6 open flag.
The existing game protocol supports eight players, 48-byte payloads, and a
64-message inbox that drops incoming packets when full. Node polling,
discovery, timeouts and close semantics are unchanged. This is the game UDP
protocol, not SC-NET, and it provides no authentication or reliable delivery.

Legacy GPU network commands and the high bank share exactly one node/inbox;
consumption through either interface removes the same packet. Their staging,
results and status are separate. Legacy pointer/length/title handling and
best-effort send-result semantics remain unchanged during migration.

==== Console bank

[cols="1,1,1,3"]
|===
|Offset |Bytes |Access |Meaning
|`0x00` |1 |RW |Read the next input byte; write an output byte
|`0x01` |1 |RW |Status: input-ready bit 0, output-ready bit 1, input-overrun bit 2
|`0x02` |1 |RW |Control: read-echo bit 0, input-receive enable bit 1
|===

All other offsets are reserved. Control starts at 3; reserved control bits are
ignored and read as zero. Status writes clear input-overrun only when bit 2 is
one, ignoring other bits. Reading status does not clear overrun or consume input.
An empty status poll while the CPU is running retains the existing host-frame
yield hint; it is not a process sleep or a guest interrupt.

The shared console has a 4096-byte receive FIFO. Host input is discarded while
receive is disabled; disabling receive does not flush queued bytes. Over-capacity
input is dropped and latches overrun until explicitly cleared. Data reads pop
one byte, return zero when empty, and echo nonzero bytes when echo is enabled.
Zero input bytes are still consumed; use status to distinguish input-ready.
Output is always ready and uses the existing 80x25 ANSI terminal, 1000-row
scrollback and 65536-byte bounded output log. Output-log overflow discards its
oldest quarter; it does not block or set input-overrun.

Data writes and echoed input update the same terminal render state and output
log as high console accesses and console syscalls. The retired low console
addresses are ordinary RAM. A rejected multibyte access consumes/echoes nothing
and changes neither control nor overrun. Input/output, cursor, escape
parser, overrun and control survive image-entry preparation; existing BIOS
handoff may separately clear input. This bank still addresses the single console;
four per-session terminals are a later OS requirement, not implemented here.

==== Firmware-text bank

[cols="1,1,1,3"]
|===
|Offset |Bytes |Access |Meaning
|`0x00` |1 |RW |Write a character/control byte; reads return zero
|`0x01` |1 |RW |Foreground palette index
|`0x02` |1 |RW |Background palette index
|`0x03` |1 |RW |Command: 1 clear, 2 enable display, 3 disable display; reads return zero
|`0x04` |1 |RW |Live cursor row, clamped to 0..24 on write
|`0x05` |1 |RW |Live cursor column, clamped to 0..52 on write
|`0x06` |1 |R |Display enabled, bit 0
|===

All other offsets are reserved. Unknown command values are no-ops; commands
commit synchronously at their byte store with no busy/status/error state.
Foreground/background accept all eight palette-index bits. Creation sets
foreground 1, background 0, cursor (0,0), disabled display and blank cells.
Image-entry preparation retains the display; the existing BIOS handoff may
separately clear and disable it. Enable/disable does not clear cells or cursor.
Clear fills all 53x25 cells using the current colors and resets the cursor.

Character output uses the existing firmware display: printable ASCII renders
directly, other bytes use `?`, with LF advancing a row while retaining column,
CR returning to column zero, backspace blanking the previous column and Tab
writing spaces to the next eight-column tab stop. A tab crossing the right edge
wraps and terminates; scrolling keeps the cursor within the fixed surface.
Writing a coordinate affects only that coordinate, preserving the other live
coordinate. All reads are side-effect-free. Invalid multibyte accesses do not
partially print, clear, enable or move the cursor.

The high console/text banks use typed device state and do not index or mirror
registers in low RAM. Their cursor readback is live and independent of the
retired low text addresses.

==== Filesystem bank

The supervisor-only filesystem bank provides bounded inline access to the
currently mounted folder disk, or the program disk when no data disk is mounted.
It calls the same `FolderDisk` containment, symlink rejection, capacity,
read-only and protected-file checks used by the protected filesystem syscalls.
It is not a user authorization boundary; multiuser permissions and the
protected user filesystem service are not yet implemented.

[cols="1,1,1,3"]
|===
|Offset |Bytes |Access |Meaning
|`0x00` |1 |W/R0 |Commit staged operation with value 1; reads return zero
|`0x01` |1 |R |Status: 0 success, 1 invalid command/operation, 2 invalid request/size, 3 no mounted disk, 4 filesystem operation rejected/failed
|`0x02` |1 |RW |Operation: `0x41` list, `0x42` read, `0x43` write, `0x44` mkdir, `0x45` delete, `0x46` rename, `0x47` stat
|`0x04` |2 |RW |List entry index, unsigned big-endian
|`0x08` |4 |RW |Read offset, unsigned big-endian
|`0x0c` |2 |RW |Transfer length, unsigned big-endian, maximum 512
|`0x0e` |2 |R |Operation result: entries/bytes, or 5 for stat
|`0x10` |4 |R |File size, unsigned big-endian
|`0x14` |2 |R |Response byte count
|`0x18` |128 |RW |ASCII NUL-terminated source path
|`0x98` |128 |RW |ASCII NUL-terminated rename destination path
|`0x120` |512 |RW |Inline write/read/list/stat data window
|===

All multibyte registers are unsigned big-endian. Creation zeros staging and
results; state survives image entry. Paths must contain a NUL in their 128-byte
window, have only zero bytes after the terminator, and be ASCII. The empty path
is valid only for listing the disk root. The command register accepts only 1;
reads return zero. Reads never touch the host filesystem. Invalid command or
operation returns status 1 before mount/path lookup; reads/writes over 512 return
status 2 before lookup or mutation; no mounted disk returns status 3. Other path,
protection, capacity, host I/O and metadata errors return status 4 and are logged.
Failures clear result, file size and response length but retain staged registers
and data. A successful command clears and replaces the data window atomically.
An invalid wide store faults before the command executes or staging changes.

List uses the path as a directory (empty means root), returns the total entry
count and encodes the staged index into data as `name NUL`, directory byte
(0 file, 1 directory), and 32-bit big-endian size. An out-of-range index returns
one zero byte. Read returns up to the staged length from the staged 32-bit offset,
with byte count in result and 32-bit file size. Write replaces the whole file
from the first staged `length` bytes; file size/result equal that length. Transfer
lengths above 512 are rejected. `mkdir`, delete and rename use the
corresponding protected folder-disk operations; delete accepts files or empty
directories and rename does not replace existing entries. Mutation of
`main.bin` and `kernel.bin` is forbidden. Stat returns result 5 and a five-byte
response: directory flag then 32-bit size. Root-level `disk.json` remains
hidden by listing and protected by the existing disk implementation. No host
paths or unchecked guest pointers are exposed through this bank.

The retired low disk register window is ordinary RAM and has no device handler.
This bank does not implement ownership, chmod/chown, cwd,
atomic replacement, credential metadata or user-mode access; those belong to
the later protected filesystem service.

==== Firmware gateway

The supervisor-only gateway uses request-local firmware handlers shared with
legacy BIOS operations. It does not forward high registers through legacy RAM
or accept guest pointers. Firmware management is not a user device service.

[cols="1,1,1,3"]
|===
|Offset |Bytes |Access |Meaning
|`0x00` |1 |RW |Command byte, reads zero
|`0x01` |1 |R |Last command status: 0 success, 1 failure (details in debug console)
|`0x02` |2 |RW |Staged disk/setting index
|`0x04` |2 |R |Disk count from enumeration/reload
|`0x06` |1 |RW |Startup selector: 0 selector, 1 preferred-disk boot
|`0x08` |2 |R |Response byte length excluding NUL, zero on failure/no response
|`0x0e` |1 |R |Additional-setting count from enumeration/reload
|`0x10` |17 |RW |Staged network name (up to 16 printable ASCII bytes plus NUL)
|`0x30` |42 |RW |Staged additional-setting record
|`0x100` |512 |R |Inline NUL-terminated response window
|===

All multibyte registers are unsigned big-endian. All remaining offsets are
reserved, including old BIOS pointer/capacity and host UI marker offsets.
Creation zeros every register/window. Staging writes retain raw bytes and
have no persistence or boot effects; the command byte is the sole commit point.
Rejected wide accesses fault before changing any register or invoking firmware.
Reads never enumerate disks, reload/save settings or transfer execution.
Gateway state survives image-entry preparation, including successful boot.

Commands preserve the existing BIOS operation numbers:

* 1 enumerates disks, selects the CLI/preferred disk, and snapshots count,
  startup/autoboot choice, network name and additional-setting count.
* 2 returns the selected disk ID in the inline response.
* 3 validates and boots the selected disk through the existing image loader;
  KERNEL remains supervisor, USER enters user mode. Program/entry preflight
  happens before clearing CPU state or copying image segments.
* 4 validates and atomically saves the selected preference, startup choice,
  network name and current additional settings.
* 5 reloads the configured settings file and performs enumeration.
* 6 reads the indexed additional setting into the record.
* 7 validates and updates the named additional setting in memory; command 4
  persists it. The existing type cannot be changed.
* 8 returns the selected disk's label, capacity, read-only and boot-mode summary.
* 9 atomically saves only the selected preferred disk, retaining startup policy.

An additional-setting record has 17 name bytes at offset 0, type at 17
(0 boolean, 1 string, 2 signed integer), and 24 value bytes at 18.
Name/value must be NUL-terminated; boolean values are `Yes`/`No`, integers are
signed decimal i64, and names/string values retain the existing bounded
printable-ASCII settings validation. There are at most eight additional settings.
The startup selector and name are checked only by operations that use them;
network-name processing uses the first 16 bytes, stopping at NUL.

Every command reports success/failure synchronously. Invalid commands, indices,
configuration, settings types, I/O and oversized responses fail explicitly.
Responses are at most 511 bytes plus NUL; success zero-fills the window and
reports the length. Success without text clears the window/length. Failure sets
status 1 and length zero but retains prior staging, snapshots and response bytes.
Do not treat retained response bytes as a successful result after failure.
No error text is truncated into a success response. Persistent settings use the
existing atomic save; failed validation/save does not replace active settings.
Boot retains existing SC-NET name-conflict checks, text/console handoff and
diagnostics. This gateway does not claim that protected normal USER startup or
revision-2 image migration is complete.

Legacy BIOS pointer outputs remain RAM-only and validated by their frontend.
The two frontends share configuration, disk discovery and boot/persistence
handlers, but not staged bytes or response/status registers. Legacy firmware
and host UI marker aliases remain until the coordinated migration.

==== Clock/random bank

[cols="1,1,1,3"]
|===
|Offset |Bytes |Access |Meaning
|`0x00` |1 |RW |Capture command: bit 0 snapshots time, bit 1 advances and snapshots random
|`0x04` |4 |R |Captured unsigned monotonic milliseconds, modulo `2^30`
|`0x08` |2 |R |Captured unsigned host frame counter, modulo `2^16`
|`0x0c` |3 |R |Captured UTC seconds, minutes, hours, one byte each
|`0x10` |4 |R |Captured unsigned 32-bit deterministic random value
|===

All multibyte values are big-endian. All other offsets are reserved. The capture
register reads as zero; reserved command bits are ignored. Writing bit 0 samples
all time fields together without advancing random. Writing bit 1 advances the
shared xorshift32 generator once and replaces only the random snapshot. Setting
both bits performs both operations synchronously at the command-byte commit.
Every byte of a multibyte store is validated first: a store spanning the command
and a reserved offset faults without sampling time or advancing random.

All snapshot fields start at zero and remain unchanged until the corresponding
capture command. Reads have no side effects; bytewise, unaligned and repeated
reads cannot tear a snapshot as time advances. All snapshot writes fault as
read-only. There is no busy state, asynchronous completion or error/status
register; undefined offsets and access violations use the common device faults.

Monotonic time uses the same CPU-lifetime epoch and 30-bit rollover as the
monotonic-milliseconds syscall. Frame count uses the existing host frame updates,
not executed instructions or wall-clock seconds. UTC comes from the last host RTC
update (zero before the first update), retaining the existing runtime/gallery
clock update cadence. Midnight wraps to 00:00:00. Clock snapshots, live RTC,
epoch, frame count and random state survive image-entry preparation.

Random uses the existing deterministic xorshift32 sequence (shifts 13, 17, 5),
initially seeded with `0x16c0ffee`. It is intended for guest games, not passwords,
salts, security tokens or entropy. Legacy GPU random commands and high random
captures advance the same sequence; legacy GPU commands do not overwrite a high
snapshot. Legacy GPU ticks/RTC commands use the same frame counter/live RTC,
without changing captured time. Runtime and gallery RTC producers update typed
clock state and latch the existing RTC interrupt; low RTC reads use that state
instead of RAM. Migration-time supervisor low RTC writes retain their prior
byte-write behavior; direct host RAM mutation is no longer a clock device API.

The instruction decoder must distinguish an invalid or unavailable encoding
from a halt. In the target architecture, an invalid encoding raises an illegal
instruction exception. Arithmetic, branch, load/store, and flag behavior is
defined by the individual ISA operation; privileged behavior is additionally
constrained by the rules below.

== Executable image format

Offline build tools emit the version 3 `SC16IMG3` container for machine
revision 2. All multibyte container fields are unsigned big-endian values. The
20-byte header contains:

[cols="1,1,2"]
|===
|Offset |Size |Value

|0 |8 bytes |ASCII magic `SC16IMG3`
|8 |2 bytes |Format version, exactly 3
|10 |2 bytes |Required machine revision, exactly 2
|12 |4 bytes |30-bit entry-point address
|16 |4 bytes |Load-segment count, from 1 through 65,536
|===

Each segment is encoded as a 20-byte header followed by exactly the declared
number of data bytes:

[cols="1,1,2"]
|===
|Offset |Size |Value

|0 |4 bytes |Fixed load address
|4 |8 bytes |Data length in bytes; zero is invalid
|12 |4 bytes |Required alignment, a power of two from 1 through 1 GiB
|16 |1 byte |Permissions: bit 0 read, bit 1 write, bit 2 execute
|17 |3 bytes |Reserved; required to be zero
|===

At least one permission bit must be set. Every segment address must satisfy
its alignment. Segment ranges must fit below `0x3ff00000`, must not
overlap, and their combined data length must not exceed 1023 MiB. The entry point
must lie inside an executable segment. Unknown permission bits, invalid
alignment, unknown versions, nonzero reserved fields, truncated data, excess
segments, and trailing bytes are errors. There is no BSS or relocation table:
segments are loaded at their encoded addresses, and the offline assembler and
compiler must resolve every reference before emitting the image. An unresolved
reference is a build error. Current C builds are single translation units;
multi-translation-unit linkage remains tracked separately in the C90 roadmap.
`SC16IMG1`, `SC16IMG2`, unknown machine revisions and unversioned raw binaries
are rejected; no compatibility reader is provided.

CPU loading validates every segment and the entry point against configured RAM
before copying any segment. Direct and folder-disk launch, including BIOS
selection, perform that check before preparing image-entry state. Rejected
bounds therefore preserve RAM, registers, privilege, MMU state, and loaded-image
metadata; launch diagnostics may still be appended to the debug log.
Segments crossing the high device-aperture boundary are invalid even with
the default 1 GiB host backing.

Image permissions describe the intended mapping. The current loader preserves
them. The MMU enforces present, writable, user, and executable permissions
when a supervisor enables translation and installs mappings. Existing
generated assembly/C images use read/write/execute permissions because their
current layout can combine code and mutable data. The container does not
select privilege: the fixed folder-disk rule selects `kernel.bin` as
supervisor code or `main.bin` as user code. The current BIOS user boot path
does not yet build an address space automatically; user mode without MMU
translation is compatibility mode, not memory isolation.

`sc16asm` assembles an assembly source to this container. `sc16build` compiles
the currently supported C subset, assembles source, or wraps a flat binary,
then writes the same container; `sc16build package-disk` additionally creates
a version 1 folder-disk manifest and its fixed-name executable. These are
offline developer tools. BIOS selection reads only the prebuilt image and
never invokes a compiler or assembler.

== Reset and firmware entry

On cold reset, hardware initialization resets the CPU and devices, then loads
the required emulator-wide `firmware/bios.bin` at physical address zero. Missing or
malformed firmware is shown as a recoverable BIOS startup error; there is no
source-compilation or host-selector fallback. CPU state is:

* PC = 0; R0-R7 = 0; flags clear.
* Supervisor (kernel) mode; interrupts disabled.
* MMU disabled, with addresses translated identically to physical addresses.
* SP and the privileged kernel-stack pointer (KSP) point to the top byte of
  usable RAM (`0x3fefffff` with default backing). The stack grows toward lower
  addresses; code must reserve space before accessing words at SP.
* Interrupt-pending state and device control registers are reset to their
  documented power-on values.

The common firmware image starts at address zero and continues executing until
it launches a selected image. The guest BIOS renders its selector through the
character-cell device, polls the keyboard device, and uses the supervisor-only
firmware service at +0x3ff0b000+ to enumerate candidate disk IDs, display the
selected manifest's label, capacity, write policy and boot mode, and boot the
selected folder. The service validates the selected manifest and fixed
executable rule, loads the prebuilt image, mounts the disk, and transfers
execution in the mode selected by the executable name. The host does not
render or drive the disk selector. Neither firmware nor the service compiles
or assembles guest source during boot. KERNEL images are trusted supervisor
code. `firmware/bios.bin` is always counted as trusted firmware and runs in kernel
(Supervisor) mode; this is a trust-policy assumption, not a signature check. The current
design does not claim authenticated boot or memory isolation. Firmware may
enable interrupts only after its handlers and kernel stack are ready.

For the BIOS firmware gateway, write the operation number to byte
`0x3ff0b000`; byte `0x3ff0b001` reports success (0) or failure (nonzero). The
selected disk index is the big-endian word at `0x3ff0b002`. Operation 4 saves the
settings menu, including startup policy byte `0x3ff0b006`; operation 9 saves only
the preferred disk and deliberately leaves startup policy and other settings
unchanged. Enter on the Boot Device row uses operation 9 before booting, so a
disk index cannot be mistaken for the 0/1 startup policy.

The BIOS reads persistent settings from `config/bios.json`. Missing
settings use defaults; malformed settings are reported rather than overwritten.
The BIOS menu can remember a preferred disk, choose selector or automatic
startup, and edit a 1-16 character SC-NET node ID. If unset, a random
`SC16-`-prefixed hexadecimal ID is generated. This ID identifies the emulator
on SC-NET; it is separate from network titles supplied by guest applications.
Up to eight additional named settings support boolean, signed integer, and
up-to-16-byte printable ASCII string values. They are shown in the BIOS list
and are written only after an explicit save action.
When automatic startup is enabled and the preferred disk exists, firmware
provides a five-second startup window; pressing Space during it enters setup
instead of booting the disk.

== Privilege and control state

The processor has two modes: supervisor (kernel) and user. Reset enters
supervisor mode. `EI`, `DI`, `RTI`, IDT installation, MMU control, address-space
switching, and kernel mapping operations are supervisor-only. A user attempt
raises a protection exception without applying the requested mutation.
Guest supervisor code installs an IDT with `LIDT Rn`, enables translation with
`MMUON Rn`, changes the active page-directory root with `MMUSWITCH Rn`, and
disables translation with `MMUOFF`. `LIDT`, `MMUON`, and `MMUSWITCH` take an
even register whose pair holds the 32-bit address/root. `ENTERU Rn, Rm`
validates and enters user mode with each 32-bit address in an even/odd register
pair (high word first); both starting registers must be even. These instructions use the
same validation as the corresponding CPU control APIs.
`STARTU Rn, Rm` creates and activates a scheduled user task with those entry
and stack addresses, using the active address space and kernel stack.
It opts that task into the emulator-backed scheduling and syscall extension.
`ENTERU` does not create a host task: a guest kernel can instead own scheduling,
save registers on timer entry, change its page-directory root, select a saved
supervisor stack, and resume with `RTI`.
High-aperture MMIO access is rejected in user mode, including translated
aliases. The remaining low graphics register window is supervisor-only.
Retired low console/text, interrupt/clock/fault, BIOS and disk addresses are
ordinary RAM rather than device aliases. User programs use only typed,
validated syscall services; there is no generic register or physical-memory
access syscall.

User instruction fetches, loads, and stores may access only user-permitted
memory when MMU translation is enabled. Page permissions apply to every byte
of multi-byte accesses. The supervisor-only `ENTERU` instruction validates the entry point and stack,
including their page permissions when translation is enabled. `SVC` is
encoded as `0x0080` and dispatches through
vector 128. For emulator-managed tasks, ABI version 1 uses this instruction for
the syscall interface below; R7 zero retains ordinary guest-handler delivery,
and unknown nonzero ABI versions are rejected. Without a host-managed task,
`SVC` always enters the guest vector handler, regardless of R7. User register
contents must not opt a guest-written kernel into host syscall dispatch.
Do not treat the legacy no-MMU user mode as an isolation boundary.

With translation enabled, user entry validation uses the installed user and
execute page permissions, not a comparison of the virtual PC with physical
image segment addresses. This permits kernels to relocate user code or load
new code into allocated frames. Without translation, the initial entry must
still belong to an executable loaded-image segment when image metadata exists.

== Exceptions and interrupts

Synchronous faults are precise: the saved PC identifies the faulting
instruction so the kernel can repair the condition and retry or terminate the
task. An interrupt is taken at an instruction boundary and saves the next PC.
IDT descriptors are 8 bytes and the 256-entry IDT is aligned to 2 KiB. Bytes
0-3 contain the big-endian 30-bit handler address; byte 4 contains present in
bit 7, DPL in bits 1-2, and trap-gate type in bit 0; all other bits and bytes
5-7 are reserved and must be zero. Vectors 0, 1, and 2 are illegal-instruction,
protection, and page-fault exceptions. Hardware vectors are keyboard 32, RTC
33, and PIT 34; vector 128 is `SVC`. Supervisor APIs install the IDT and
descriptors. A user `SVC` requires descriptor DPL 3. Missing descriptors are
reported as unhandled; malformed descriptors or invalid event entry stop the
CPU as a double fault.

Interrupt gates clear the global interrupt-enable bit on entry; trap gates
preserve it. `RTI` validates the saved frame and restores the prior mode, PC,
flags, interrupt-enable state, and stack. Pending hardware sources are
prioritized keyboard, PIT, then RTC and the selected pending bit is
acknowledged at delivery. Nested delivery stays disabled until a handler
explicitly enables interrupts. Firmware must install valid handlers before
enabling an interrupt source.

Every exception or interrupt creates a 16-byte, big-endian frame on the
supervisor stack. With the MMU enabled, SP and KSP are virtual addresses and
event frames use supervisor translation, just like guest stack instructions.
All frame bytes are checked before writing, including frames crossing pages;
frames must reside in writable RAM, not MMIO. The graphics framebuffer is
device-owned state and has no physical RAM address. RTI reads
the frame through the active supervisor mapping and validates the restored executable PC and writable
stack before changing context. Invalid frames or return targets stop the CPU
with a double fault. At the frame address, increasing offsets contain:

[cols="1,1,2"]
|===
|Offset |Size |Value

|0 |4 bytes |Saved PC
|4 |2 bytes |Saved flags (Z, C, N, V in bits 0-3)
|6 |2 bytes |Saved status: prior mode in bit 0, prior interrupt-enable in bit 1
|8 |4 bytes |Prior active SP
|12 |2 bytes |Exception cause or interrupt vector
|14 |2 bytes |Entry kind: synchronous exception or interrupt
|===

The stack grows downward; entry lays out the frame so its PC is at offset zero.
An event from user mode saves the user SP, switches to KSP, and builds the
frame there. An event from supervisor mode builds the frame on the current
supervisor stack. Return is supervisor-only: it validates and consumes the
frame, restores flags and PC, then restores the prior mode and stack. Returning
to user mode restores the saved user SP while retaining the post-frame KSP.

An invalid vector, malformed return frame, or fault during entry/return is a
double fault. A double fault stops the affected CPU rather than attempting a
second untrusted stack transition. The kernel must not resume by treating a
double fault as an ordinary user exception.

Events from user mode save the user SP, switch to KSP, and build the frame
there. Events from supervisor mode use the current supervisor stack. The
frame layout above is implemented. Missing handlers are not replaced by
legacy fixed-vector words.

The PIT period is a 16-bit value at `INTERRUPT_PIT_PERIOD`; zero disables
periodic generation. One timer tick is one completed emulator instruction,
including headless execution, so no host wall clock is involved. The
`INTERRUPT_PIT_ENABLE` register masks delivery without stopping counting.
Pending sources are read from `INTERRUPT_PENDING` and acknowledged through
`INTERRUPT_ACK`. Pending state remains latched while masked and is cleared on
delivery. A scheduler-managed task context is preempted at the validated PIT
boundary; otherwise delivery enters the installed vector handler.

The emulator-side scheduler context contains R0-R7, PC, SP, KSP, flags,
privilege mode, interrupt-enable state, MMU-enabled state, and page-directory
identity. The scheduler provides runnable, running, blocked, and exited states
with round-robin selection, yield, exit, block, and wake operations. The
versioned guest syscall interface below exposes the supported process and
synchronization services. The Phase 9 lifecycle fixture and Phase 10 SisuOS
demonstration boot through the common BIOS and execute guest workloads; neither
example establishes general-purpose OS readiness.

The independent hardware regression in `tests/preemptive_hardware.rs` does not
create host tasks or invoke host scheduling services. Its guest kernel installs
the IDT and two page directories, then handles PIT interrupts in assembly to
save registers, switch address spaces and supervisor stacks, and restore the
next user context with `RTI`. Two user loops share virtual addresses but have
different physical code, data, and stack pages. The test checks continued
progress, register and stack preservation, and guest-owned SVC handling.
Run it with `cargo test --test preemptive_hardware`. This is a hardware
acceptance fixture, not a replacement SisuOS implementation.

== Memory translation

Reset starts with translation disabled. The target MMU uses 4 KiB pages and a
two-level table: 9 directory-index bits, 9 table-index bits, and 12 offset
bits. Each directory and table has 512 32-bit entries and occupies 2 KiB. An
entry contains an 18-bit physical frame number in bits 12-29 and flags in the
low bits:

* bit 0: present;
* bit 1: writable;
* bit 2: user accessible;
* bit 3: executable;
* bits 4-11 and 30-31: reserved and required to be zero.

Effective permissions are the intersection of the directory and table entry
permissions. Missing mappings and read, write, execute, or privilege violations raise page
faults with the access type and virtual address. Page table roots and MMU
control state are supervisor-only. Translation has no TLB; address-space
changes take effect immediately. The Rust `FrameAllocator` and
`PageMemoryManager` allocate and account for frames, create/destroy roots,
allocate and map pages, map borrowed frames, change permissions, unmap pages,
release empty page tables, and construct identity-mapped ranges. Borrowed
physical frames remain caller-owned; allocated mappings are released on
unmap. Unmapped pages can serve as guard pages. These are kernel primitives;
the BIOS does not yet establish a protected address space as part of normal
user boot.

The emulator-managed process allocator reserves the remaining low graphics
register window before allocating page tables or process pages.
The high device aperture is excluded from usable RAM, images, and page
allocations. Graphics pixels live in a device-owned buffer, independent of
backing RAM size and unaddressable by guest loads, stores, DMA-like operations
or process mappings.
Addresses formerly occupied by the framebuffer are ordinary RAM; they do not
alias the device-owned pixels.

== Device access

The emulator exposes the revised device banks through high-address,
supervisor-only MMIO. The remaining low graphics register window is
migration-only and supervisor-only; retired low control, terminal, BIOS and
disk addresses are RAM. The folder-filesystem gateway validates user pointers
against the active MMU mappings, including noncontiguous buffers, when paging
is enabled. The retired low disk window has no command handler. This device
gateway remains distinct from the general syscall ABI. With translation
disabled, ordinary RAM is not isolated from user code.

Validated buffer services reject both virtual and translated physical addresses
in the high device aperture and the remaining low graphics window. This applies
to paths, arguments, console and file transfers, process reports, networking,
and folder gateway transfers, including requests made by supervisor code through those
buffer helpers. Checks cover every requested byte before consuming input or
modifying output; crossing from ordinary RAM into a device range is an error,
not a partial transfer. Direct access to the remaining legacy low graphics
window is not a supported user interface.

== System-call ABI version 1

User software invokes `SVC` (`0x0080`) with a present vector-128 IDT
descriptor whose DPL is 3. The processor enters supervisor mode on KSP and
validates the event frame. For ABI version 1, emulator-side kernel services
dispatch the call in Rust and return through that frame; the configured guest
handler is validated but its instructions are not executed for ABI calls.
`R7` contains the ABI version, `R0` the syscall number, and `R1` through `R6`
the arguments. `R0` is the result register. Errors are negative errno-style
values; unknown numbers or unsupported nonzero versions return `-EINVAL`.
Register arguments contain complete 30-bit pointers and scalar values; C
`long` arguments use the target's high-word/low-word stack representation,
which the native wrappers combine before `SVC`.

The original `spawn` and `spawn_arg` supply the executable path as argument
zero and retain their existing scalar startup behavior. The boot process uses
its disk ID (or `init` without a disk) as argument zero. Argument contents are
kernel-owned per-process copies, not aliases into the spawning process's
address space. `sc16_spawn_exec`, `sc16_argument_count`, and `sc16_argument`
expose this interface to guest C; the shell remains responsible for tokenizing
quotes and constructing the argument block.

Every user pointer is range-checked against the active address space before
use. Paths are ASCII, null-terminated, and limited to 128 bytes; read/write
transfers are limited to 4096 bytes. Handles 0, 1, and 2 are nonblocking
console input, console output, and console error; allocated folder-file
handles start at 3 and belong to one process. Open flags are READ=1, WRITE=2,
CREATE=4, TRUNCATE=8, and APPEND=16. Append writes select the current file end
for each write. Seek is file-only, accepts signed 32-bit offsets, and rejects
positions outside 0..2^31-1. `mmap` permission bits are READ=1, WRITE=2, EXEC=4; mapped
pages belong to the caller's address space. Sleep advances on deterministic
emulator instruction ticks. Wait accepts only a direct child and reaps it
after collecting status. Semaphore CREATE returns a new ID; WAIT, POST, and
DESTROY return zero on success.

Semaphore operations are CREATE=0, WAIT=1, POST=2, and DESTROY=3. The creating
process owns a semaphore; WAIT blocks at count zero, POST wakes one waiter, and
owned semaphores are removed when that process exits. In the C wrapper,
`sc16_mmap` returns the mapped address as `long` or a negative error; the
remaining wrappers return the corresponding ABI result. The C interface in
`toolchain/include/sc16_syscall.h` provides SC-16-specific wrappers. The separate
`toolchain/include/sc16_net.h` wrappers expose SC-NET discovery, peer messaging, and
nonblocking receive; names occupy fixed 16-byte slots and payloads are limited
to 1024 bytes. SC-NET uses a separate host UDP service on port 47017, distinct
from guest application networking on port 47016. BIOS startup refuses to boot
when another active emulator advertises the configured node name. SC-NET is a
transport service, not the guest application's network protocol.

The compiler links a file-stream runtime when a C translation unit uses one of
its supported file APIs: `fopen`, `freopen`, `fclose`, `fgetc`, `fputc`,
`fread`, `fwrite`, `fseek`, `ftell`, `ungetc`, `clearerr`, `feof`, and
`ferror`. These streams use the current folder-backed disk and syscall ABI;
they are unbuffered. `remove` is explicitly unsupported and reports `ENOSYS`.
This is a limited hosted-C subset, not complete C90 `stdio` or a hosted
environment; see `docs/c90_todo.adoc`.

== Firmware text display

The guest BIOS writes its selector to the guest-visible character-cell
surface, rendered in the emulator's 640 by 480 main window. The logical
surface is 53 columns by 25 rows, with 12 by 16 pixel cell slots. It renders
printable ASCII bytes 32-126 using the embedded 5 by 7 font doubled to 10 by
14 pixels; other input bytes render as `?`. The background is black and the
firmware selects bright green text. Serial diagnostics and guest pixel
graphics remain separate surfaces.

The guest-visible character-cell display uses a separate surface with this
contract:

* The surface is 53 columns by 25 rows. Each cell occupies a 12 by 16 pixel
  slot at 640 by 480, and uses the same embedded 5 by 7 glyphs doubled to 10
  by 14 pixels. At 320 by 240 the same surface is scaled to 6 by 8 pixel cells.
* Character data is one byte. Printable ASCII bytes 32-126 render as their
  glyph; other bytes render as `?`. Control bytes are interpreted by the text
  service: line feed (10), carriage return (13), backspace (8), and tab (9)
  do not occupy cells.
* Foreground and background colors are 8-bit indexes into the current system
  palette. Guests can select the colors applied to subsequently written cells.
* The cursor is a row/column pair. Line feed advances one row without changing
  the column; carriage return moves to column zero; backspace moves left and
  blanks that cell; tab advances to the next multiple-of-eight column. Text
  written at the last column wraps. Advancing beyond the last row scrolls all
  rows up by one, clears the final row using the current background, and leaves
  the cursor there.
* The service is exposed through guest-visible byte registers at `0x3ff0a000`:
  data at offset 0, foreground at 1, background at 2, control at 3, row at 4,
  and column at 5. Control commands 1, 2, and 3 clear, enable, and disable the
  surface. Cursor coordinates are zero-based and clamped to the surface. The
  register definitions are in +toolchain/include/guest_text.h+.
* The text surface is overlaid after pixel graphics; enabling it does not
  disable or replace the existing game graphics window. It is disabled on
  reset and is not the serial diagnostics/Bug Monitor channel.

This byte-register interface is the initial guest display API; it is not a
memory-protection boundary. User access remains limited to the allowed text
registers; the syscall ABI does not yet mediate display ownership.

== Supported versions and compatibility boundary

The currently supported encoded formats and interfaces are:

[cols="1,2"]
|===
|Interface |Supported version or status

|Machine/ISA
|Machine revision 2; device ABI 1.

|Executable image
|Version 3 (`SC16IMG3`), machine revision 2. Earlier and raw images are rejected.

|Folder-disk manifest
|Version 1 (`disk.json`).

|BIOS boot convention
|Selects `kernel.bin` or `main.bin` from a version 1 folder disk. The boot
convention has no independent version field.

|System-call ABI
|Version 1. Unknown or unsupported ABI versions return `-EINVAL`.
|===

Reset initializes PC to zero and SP/KSP to the top of configured memory,
enters supervisor mode, and leaves interrupts and MMU translation disabled.
Privilege transitions, IDT delivery, deterministic PIT timing, scheduler
contexts, page translation, page faults, frame/mapping helpers, and syscall ABI
version 1 are implemented and tested. The BIOS-booted SisuOS example verifies
protected kernel startup, shell I/O, timer scheduling, child execution and
return to its shell. The current implementation is not yet a general-purpose
operating system:

* The minimal kernel example uses static page tables. The syscall fixture builds
  its initial tables at runtime and exercises guest-visible `sys_mmap`; frame
  allocation and mapping are emulator-side kernel services, not a guest-written
  allocator. Neither example is a general-purpose kernel.
* Normal BIOS USER boot does not install MMU mappings and must not be described
  as process-isolated.
* A BIOS-booted guest workload verifies spawn, yield, sleep, wait, console/file
  I/O, and exit together, but this sample does not establish general-kernel
  robustness.
* SisuOS is a demonstration shell with fixed `help`, `list`, `info`, `ps`,
  `run demo`, and `run demo X` commands. Its program list is static; it does not provide a
  general command interpreter, package manager, or persistent user accounts.
* The BIOS-booted workload triggers a supervisor-only read and verifies that the
  sample handler skips the faulting instruction. This single recovery policy is
  not a general page-fault or process-termination policy.
* Authenticated or secure boot is not implemented.
* The syscall ABI explicitly leaves file removal unsupported; the Rust C
  frontend is a tested subset rather than a claim of complete C90 support.
